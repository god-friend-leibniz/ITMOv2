# ADR: решение для первого рабочего сценария

- Статус: proposed
- Дата: [нужно назначить]
- Ответственные: [нужно назначить]

## Контекст

- Проблема: инженеру-ревьюеру нужен короткий доказательный черновик комментария по diff PR; сейчас черновик формируется вручную, что замедляет старт ревью.
- Пользовательский сценарий: отправка `POST /api/reviews` с JSON, содержащим ключ `diff` (строка с diff); система формирует промпт, вызывает LLM и возвращает `{"comment": "<черновик>"}`; человек проверяет и принимает решение по PR.
- TO BE: синхронный HTTP-сервис, который анализирует только переданный diff, строит промпт и запрашивает LLM; финальное решение остаётся за человеком.

## Решение

Принять синхронный поток для первого сценария:
- Контракт:
  - Вход: `POST /api/reviews` с JSON телом, где `payload["diff"]` — строковый diff PR.
  - Выход: JSON с ключом `comment`, содержащим строковый черновик.
- Компоненты и взаимодействие:
  - API-обработчик `POST /api/reviews` получает `payload`.
  - `ReviewService.review(diff)` формирует промпт вида `Review this pull request and find problems:\n{diff}` и вызывает `LLM.generate(prompt)`.
  - Ответ LLM оборачивается как `{"comment": answer}` и возвращается клиенту.
- Интеграция:
  - `ReviewService` зависит от интерфейса `LLM` (протокол/интерфейс), что позволяет подменять реализацию (мок/реальный клиент).
  - Инжекция зависимости выполняется на уровне слоя зависимостей приложения.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Прямой вызов LLM из API-обработчика | Смешивает транспортный слой и доменную логику, ухудшает тестируемость и переиспользование; усложняет подмену LLM-клиента. Для первого сценария достаточно явного сервисного слоя. |
| Асинхронная обработка через очередь | Усложняет архитектуру (брокер, воркеры, подтверждения), вводит задержки и необходимость трекинга статуса. Для первого сценария приоритет — получить черновик в одном запросе; требований к очереди не зафиксировано. |

## Последствия и главный риск

- Положительные последствия:
  - Соответствие пользовательскому сценарию и TO BE; простота реализации и быстрый вывод первого инкремента.
  - Чёткое разделение: API ↔ ReviewService ↔ LLM (по интерфейсу), удобство мокирования.
- Ограничения:
  - Блокирующий ответ зависит от времени отклика LLM.
  - Отсутствуют ретраи, хранение истории и статусы обработки; поведение при ошибках не нормировано в рамках сценария.
- Главный риск:
  - Прямой доступ к `payload["diff"]` может вызвать ошибку доступа по ключу при отсутствии `diff` во входе (см. TRAINING_PR.diff: `return review_service.review(payload["diff"])`).
- Как проверим риск:
  - Отправить `POST /api/reviews` с телом `{}` и зафиксировать наблюдаемый результат: отсутствие `comment` и/или ошибка обработки запроса. Проверка считается пройденной, если риск воспроизводится и задокументирован.
