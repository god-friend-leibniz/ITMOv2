# Проблема и метрики

Файл ведёт OpenCode. Обсудите с агентом содержание и проверьте предложенный diff. Все дополнения и исправления поручайте агенту в чате.

## Проблема

- Пользователь: инженер-ревьюер pull request.
- Ситуация: у инженера есть diff PR; нужен короткий доказательный черновик комментария, который затем проверяет и дополняет человек.
- Что происходит сейчас: черновик формируется вручную на основе чтения diff без помощи LLM.
- Почему это мешает пользователю или бизнесу: уходит время на первоначальное формирование замечаний по diff; первичная фиксация проблем может быть неоднородной между ревьюерами.
- Что не входит в задачу: автоматический approve/merge PR; изменение кода; интеграции с внешними системами, включая GitHub и трекеры; гарантии конкретных HTTP-статусов или SLA; аутентификация и авторизация; хранение истории ревью.

## Метрики

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---|---|---|---|
| Доля успешных ответов с черновиком | Отправить N запросов `POST /api/reviews` с валидным JSON `{"diff": "<строка с diff>"}`; успех — ответ содержит ключ `comment` со строковым значением. | Увеличение доли успешных ответов. | На стенде при приёмке первого сценария и далее периодически. | Ответ API сервиса. |
| Время получения черновика | Замерить клиентское время от отправки `POST /api/reviews` до получения ответа с ключом `comment`. | Сокращение времени относительно ручного формирования черновика. | При приёмке и в регрессе. | Таймстампы клиента или инструмента вызова API. |
| Доля ошибок из-за некорректного входа | Отправить запросы без ключа `diff` или с нестроковым значением; ошибка — отсутствие `comment` и/или фиксируемое исключение доступа по ключу `diff`. | Снижение доли таких ошибок или их явная диагностируемость. | На стенде при приёмке и при изменениях контракта. | Ответ API и логи приложения. |
| Экономия времени ревьюера на первичный черновик | Сравнить время подготовки первичного черновика: до — ручной замер по нескольким PR; после — время до получения `comment` и доработки человеком. | Сокращение среднего времени. | До запуска и после запуска сценария. | Таймтрек ревьюера, опрос и клиентские замеры. |

## Почему изменение метрики подтвердит решение проблемы

- Рост доли успешных ответов и сокращение времени до получения `comment` покажут, что сервис стабильно формирует пригодный черновик быстрее, чем вручную.
- Снижение доли ошибок входа и их диагностируемость снизят прерывания работы при использовании сервиса.
- Сокращение времени ревьюера на первичный черновик покажет практическую пользу сценария.

- Для чего: подготовить черновик `problem.md` по Context Pack, diff и шаблону.
- Тип промпта: Master Prompt v3 для первой группы артефактов.
- Строка в [`prompts.md`](prompts.md): P1-04.
- Что проверил студент и какие исправления поручил агенту: согласованность метрик со сценарием, отсутствие выдуманных численных целей и сохранение финального решения за человеком.
