# StudyFlow Constitution

## Core Principles

### I. Узкие изменения на основании действующего контракта

Перед изменением поведения необходимо прочитать `AGENTS.md`, `spec.md` и `GLOSSARY.md`
из корня StudyFlow. Изменение решает конкретную согласованную задачу; поведение,
публичные контракты и данные вне её границ сохраняются. Завершённые части приложения
не перепроектируются без конкретного требования или выявленного противоречия.
Изменения архитектуры, доменных правил, API и объёма продукта отражаются в `spec.md`
в той же работе. Новые требования нельзя выводить из примеров шаблонов Spec Kit.
Это сохраняет небольшой учебный CRUD-проект и делает каждое изменение проверяемым.

Основание: `AGENTS.md`, Goal and scope и Architecture and stack в `spec.md`.

### II. Простая локальная архитектура

Сохраняется одно локальное веб-приложение на Python 3.12, FastAPI/Pydantic,
Uvicorn, Jinja2, обычных CSS и небольших JavaScript-модулях, с SQLite и локальным
stdio-процессом MCP. Зависимости ведутся через `pyproject.toml`, `uv.lock` и uv;
отдельной сборки frontend нет.

Ответственности остаются явными: `web.py` обслуживает HTML/JSON и ошибки транспорта;
`domain.py` содержит чистые правила без HTTP, SQL и MCP; `coursework.py` координирует
сценарии; `db.py` и миграции выполняют конкретные операции SQLite;
`github_mcp_client.py` и `studyflow_mcp/` образуют интеграционную границу.
Используются обычные функции, явные параметры и SQL. Абстрактные репозитории,
иерархии сервисов, DI-контейнеры, event bus, CQRS и дополнительная инфраструктура
не вводятся без обоснованной потребности согласованного изменения.
Усложнение должно решать существующую проблему, а не предполагаемую будущую.

Основание: `AGENTS.md`, Architecture and stack в `spec.md` и текущие модули приложения.

### III. Единый язык и доменные инварианты

Термины используются в смысле `GLOSSARY.md`: Course содержит Assignment,
Assignment содержит Task; checklist — коллекция задач, а не отдельная сущность.
Родители должны существовать, связи владения обязательны и неизменяемы.
Удаление курса атомарно удаляет его задания и задачи, удаление задания — его задачи.

Задача изначально не завершена; её завершение — строгий boolean, повторное завершение
безопасно, повторное открытие разрешено. Прогресс задания вычисляется по текущим
задачам: `floor(100 * completed / total)`, при пустом чеклисте — `0%` и `0 / 0`.
Счётчики отображаются вместе с процентом. Завершённым считается только непустой
чеклист, у которого завершены все задачи. Отдельный сохраняемый статус задания
или ручной переключатель его завершения не вводится; прогресс не означает сдачу,
оценку или активность GitHub. Эти правила исключают противоречащие друг другу состояния.

Дедлайн остаётся необязательной календарной датой `YYYY-MM-DD`, без времени
и часового пояса; прошедшие реальные даты допустимы. Задание имеет не более одной
ссылки на репозиторий: отсутствующее значение либо полная валидная пара owner/repo
в нижнем регистре. Один репозиторий может использоваться в нескольких заданиях.
Удаление учебных данных ничего не удаляет на GitHub.

Основание: `GLOSSARY.md`, Domain model в `spec.md`, `domain.py`, `coursework.py`
и миграции.

### IV. GitHub через изолированную границу MCP

Обычный CRUD, сохранение и проверка синтаксиса repository reference работают
без обращения к GitHub. Summary загружается или обновляется только по явному запросу.
Приложение и агент получают его через read-only инструмент `get_repository_summary`
локального stdio MCP; production HTTP-доступ к GitHub остаётся в `studyflow_mcp/`.
MCP-сервер не получает доступ к учебной базе и не выполняет записи на GitHub.
Это сохраняет одну проверяемую интеграционную границу и независимость учебных данных.

Сохраняется только ссылка на репозиторий, а не summary, GitHub-активность или токены.
Результаты MCP проверяются по опубликованным схемам. Вызов ограничен общим таймаутом,
а сессия и дочерний процесс освобождаются при успехе, ошибке и отмене.
Транзакции SQLite не охватывают сетевые вызовы. Ошибки интеграции допускают повторную
попытку, не повреждают coursework и не блокируют его CRUD. После изменения ссылки
устаревший ответ не отображается; неудачный refresh не представляет прежнюю summary
как актуальную. Stdout сервера занят протоколом, диагностика направляется в stderr.

Основание: Custom MCP integration в `spec.md`, существующий ADR 0001,
`github_mcp_client.py`, `studyflow_mcp/` и `static/repository.js`.

### V. TDD через публичное поведение

При реализации функций, исправлении поведения и добавлении интеграционных тестов
используется существующий skill `.agents/skills/tdd/`. Работа идёт вертикально:
один падающий тест поведения → минимальная реализация → успешная проверка.
Нельзя заранее писать все тесты или все слои реализации. Новые публичные границы
тестирования согласуются по правилам skill, если ещё не подтверждены в сессии.

Тесты проверяют HTTP/HTML, MCP tools, реальные stdio-вызовы, команды hooks
и пользовательское поведение браузера. Используются настоящие временные SQLite-базы;
подменяются внешние HTTP/MCP-границы, а не внутренние доменные и persistence-слои.
Ожидаемые результаты берутся из контракта и конкретных примеров, а не повторяют
алгоритм реализации. Обычный набор тестов детерминирован и работает offline;
live-проверки GitHub выполняются отдельно. Mock-покрытие не заменяет реальный stdio.
Цель — проверять результат, сохраняя свободу внутренней правки.

Основание: Testing strategy в `spec.md`, `AGENTS.md`, TDD skill и существующие тесты.

## Сохранность данных и интерфейсов

- SQLite использует параметризованный SQL, foreign keys на каждом соединении,
  атомарные мутации и rollback при ошибке. Нумерованные SQL-миграции поставляются
  в пакете и применяются вперёд без сброса пользовательских данных.
- Валидация сохраняет ограничения действующего `spec.md`: непустые обрезанные
  имена и заголовки до 200 символов, plain-text описания до 5000 символов,
  реальные календарные даты, полную пару repository reference и строгие JSON-схемы.
  Производные прогресс и summary не сохраняются в базе.
- JSON API сохраняет действующие поля, HTTP-коды и форму
  `error: {code, message, fields}` вне явно согласованного изменения контракта.
  Ошибки не раскрывают SQL, traceback или секреты и не оставляют частичных записей.
- HTML/JavaScript сохраняют экранирование пользовательского и GitHub-текста,
  подписи полей, управление с клавиатуры, явные empty/loading/error-состояния,
  введённые значения при ошибке и защиту от повторной отправки во время запроса.
  Удаление требует существующего подтверждения с описанием каскада.
- Изменения списков сохраняют существующий фильтр завершённости, область курса
  и контракт JSON-списка за пределами явно согласованной задачи. Сортировка,
  фильтрация или представление не создают независимый доменный статус задания.
- Приложение остаётся локальным и привязанным к loopback. Публичный хостинг,
  аккаунты, совместная работа, оценки, уведомления, OAuth, приватные репозитории,
  GitHub-записи и фоновое обновление требуют отдельного решения об объёме продукта.
  Токены остаются в окружении процесса и не попадают в Git, ответы или evidence.

Основание: Persistence, Architecture and stack, API and use cases, Error handling
и Non-goals в `spec.md`; текущие схемы, маршруты, шаблоны и JavaScript.

## Порядок работы и проверка

1. Работать из StudyFlow с действующими инструкциями и lockfile. Согласовать узкую
   границу изменения; не менять архитектуру или соседнее поведение попутно.
2. При изменении терминов, владения, инвариантов или архитектурных решений применять
   существующий domain-modeling skill. Глоссарий содержит только язык предметной
   области; ADR добавляется только по критериям skill, а не для каждой правки.
3. Сохранять установленные skills, hooks и их определения. Редактировать последовательно,
   читать feedback до несвязанной работы; не отключать hooks и не ослаблять тесты
   ради прохождения проверки. Ожидаемый red в TDD ведёт к минимальной реализации,
   неожиданный сбой — к разбору и исправлению.
4. Быстрая проверка после значимых правок — действующий PostToolUse hook с offline-тестами.
   Перед завершением — действующий Stop gate: `uv run pytest -q`,
   `uv run pytest -q -m browser`, `uv build`. Все три этапа должны пройти;
   отсутствие среды, таймаут или отсутствие собранных тестов не означают успех.
   Финальная проверка использует frozen lockfile и offline-режим; зависимости
   и браузер подготавливаются заранее, пользовательская база не сбрасывается.
5. Если автоматический вызов недоступен, выполнить тот же обработчик вручную:
   `python3 scripts/verify_before_finish.py`. Проверять feedback и коды всех этапов,
   а не только exit code обработчика. Ручной запуск не доказывает активацию hook.
6. В результате работы указывать фактически выполненные проверки и ограничения.
   Сохранять исторические результаты, отличать планы от наблюдений; не выдумывать
   TDD, MCP или автоматическое срабатывание hooks. Точные команды и настройки среды
   остаются в `AGENTS.md` и существующих обработчиках.

Основание: `AGENTS.md`, Automatic verification hook и Testing strategy в `spec.md`,
`.codex/hooks.json`, `scripts/verify_after_change.py` и `scripts/verify_before_finish.py`.

## Governance

Эта конституция фиксирует общие принципы существующего StudyFlow. Детальные
поведенческие контракты находятся в `spec.md`, определения — в `GLOSSARY.md`,
операционные инструкции — в `AGENTS.md`. Конституция не подменяет спецификацию фичи
и сама по себе не разрешает реализацию, рефакторинг или расширение продукта.

При проверке изменения необходимо сопоставить его с этими принципами и действующим
контрактом, проверить отсутствие несогласованного расширения и результаты проверок.
Если документы и код расходятся, противоречие явно описывается; существующее правило
нельзя молча заменить предположением или примером из шаблона.

Поправка к конституции указывает причину, основание в согласованном требовании
или обнаруженном противоречии и затронутые принципы. Менять принципы попутно,
чтобы оправдать несогласованное решение реализации, нельзя. Связанные изменения
`spec.md`, `GLOSSARY.md` и `AGENTS.md` выполняются в рамках соответствующей
согласованной работы; создание конституции не требует их переписывания.

Версия следует SemVer: MAJOR — несовместимое изменение или удаление принципа;
MINOR — новый принцип или существенное расширение правил; PATCH — уточнение текста
без изменения смысла. Дата первоначального принятия сохраняется, дата последнего
изменения обновляется при поправке. Версия 1.0.0 — первое заполнение и принятие
принципов вместо штатного шаблона; предыдущей принятой конституции не было.
