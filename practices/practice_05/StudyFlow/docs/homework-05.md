# ДЗ 5: согласование и реализация списка заданий StudyFlow

Дата отчёта: 27 октября 2026 года (МСК); реализация и согласование описаны по результатам 25–26 октября. Работа выполнена в отдельных ветках `codex/hw5-ui` и `codex/hw5-logic`. В `practice_05` результат пока не влит.

## 1. Фича и разделение команд

На странице курса задания упорядочены по возрастанию дедлайна, затем идут задания без даты; одинаковые даты и отсутствие дат разрешаются числовым ID по возрастанию. Правило действует внутри каждой вкладки. Добавлена Overdue («Просроченные»): незавершённые по чек-листу задания с дедлайном строго раньше сегодняшней локальной даты компьютера с StudyFlow. Пустой чек-лист незавершён; сегодняшние, будущие, завершённые и недатированные задания в Overdue не входят. Просроченные остаются во All и Incomplete.

JSON API сохраняет прежние поля, ошибки и полный список курса в порядке ID. Нового сохраняемого статуса, миграций, зависимостей, фонового опроса или вычисления просроченности в браузере нет.

| Команда | Ответственность | Основные файлы |
| --- | --- | --- |
| UI | Карточки, четыре вкладки, URL и возврат, создание и обратная связь, empty/error/retry, клавиатура и узкий экран | `course.html`, `assignments.js`, `style.css`, `tests/test_browser.py` |
| Логика | Нормализация режима, состав и порядок, завершённость, одна актуальная локальная дата, `has_assignments`, HTTP/HTML-ошибки и no-store | `domain.py`, `web.py`, `tests/test_assignment_filtering.py` |

Команды сначала независимо описали результат, затем согласовали требования и техническую границу. UI не реализовывал серверный алгоритм, логика не подменяла настоящий UI-шаблон тестовым. G-server обозначал доступность серверного ядра; G-integrated — совместную проверку реального шаблона и поведения браузера. Интеграционные задачи UI T038–T040 ожидали дополнительных HTTP/HTML-проверок логики.

## 3. Что согласовали на границе

1. **Режим и результат.** `completion=all|incomplete|completed|overdue`; отсутствующее, пустое или неизвестное значение означает all. Сервер возвращает окончательный список, нормализованный режим и `has_assignments` до фильтрации. Это позволяет отличить пустой курс от отсутствия совпадений.
2. **Источник даты.** Один серверный результат использует одну актуальную локальную дату компьютера с StudyFlow. Браузер, UTC-дата, дата открытия формы и дата запуска приложения её не заменяют. В production используется `date.today`; публичный `local_date_provider` позволяет проверить смену дня без изменения часов ОС.
3. **Свежесть после записи.** После каждого подтверждённого создания во всех четырёх режимах выполняется свежий GET существующей HTML-страницы курса. Ответ POST подтверждает ID и сохранённое название, но не видимость. Видимость определяется наличием ID в новом серверном результате, в том числе если полночь наступила между формой, записью и чтением.
4. **Раздельные исходы.** Успешная запись очищает форму. Если последующее чтение не удалось, запись остаётся успешной: UI показывает «Задание сохранено, но список обновить не удалось», помечает прежний список неактуальным и не объявляет скрытость или новое пустое состояние.
5. **Повтор только GET.** «Обновить список» читает тот же курс/режим, не повторяя POST. Повторные запуски во время ожидания заблокированы; новая ошибка оставляет возможность чтения, успех заменяет список и определяет видимость по ID. При неизвестном сетевом исходе самой записи UI не утверждает, что запись гарантированно отсутствует, и автоматически её не повторяет.

Технически UI запрашивает полный HTML с `Accept: text/html` и `cache: no-store`; успешный серверный HTML также имеет `Cache-Control: no-store`. Проверяются статус, media type и маркеры результата. Заменяется только секция списка; формы, сообщения и retry остаются в документе. Сортировка и вычисление дат в JS не дублируются, скрипты из полученного HTML заново не подключаются.

## 4. OpenSpec и Spec Kit: сравнение выполненной работы

Одна и та же продуктовая фича **в OpenSpec была только спланирована, а реализована через Spec Kit**. Соседний архив OpenSpec относится к прежней фиче фильтрации завершённости; его реализация и старые counts не являются выполнением нового change с дедлайнами и Overdue.

Есть различие редакций: OpenSpec design предусматривает новый HTML refresh после создания в Overdue, сохраняя прежние потоки остальных вкладок. Позже согласованный контракт Spec Kit требует свежий GET после каждого создания во всех четырёх режимах и явный GET-only retry. Поэтому тексты нельзя считать полностью одинаковыми техническими экспериментами.

Для отчёта из каталога `practice_05` выполнено `openspec validate sort-assignments-by-due-date --type change --strict --no-interactive`: **exit 0**, `Change 'sort-assignments-by-due-date' is valid`. Это проверка документов, а не реализация или приёмка поведения приложения.

Число пунктов tasks не сравнивается как показатель качества или скорости: отличаются декомпозиция, число команд, редакция требований и глубина выполненных этапов. Эти наблюдения не доказывают превосходство одного инструмента.

### Converge: F1 и T041

Первый converge нашёл F1 (partial, MEDIUM), хотя обычный gate был зелёным: после создания в Completed с допустимым названием из 200 букв `A` документ при viewport 360px расширялся до **2179px**. Прежние тесты узкого экрана использовали короткий текст.

Затем отдельно добавлен вариант видимого создания во All: **2 passed, 1.71s**. Название не обрезается, глобальный overflow не скрывается; проверяются геометрия текста, ширина 360px и клавиатурный переход All. Коммит исправления: `7d43b948ba1be47e0a8747b1dcecd542455f41dc`.

## 6. Рефлексия по наблюдениям

Независимые спецификации сделали видимым разрыв между «сервер учтёт запись при следующем запросе» и обязательством UI действительно выполнить этот запрос перед выводом о видимости. Общий контракт превратил это различие в проверяемый сценарий полуночи и отдельный исход отказа чтения.

Распределение файлов и интеграционные зависимости помогли сохранить один протокол: UI дождался ядра, а логика проверила настоящий шаблон после его поставки. Analyze оказался полезен для порядка задач, а converge — для проверки результата: зелёный существующий набор не обнаружил F1 до добавления конкретного длинного названия. Локальная правка закрыла наблюдаемый дефект без расширения архитектуры.

Проверка окружения потребовала отдельной работы: наличие uv в shell не обеспечило его доступность hook, а прохождение тестов без внешнего лимита не обеспечило укладывание в gate. Поэтому counts, exits, способ запуска и ограничения записывались отдельно. Это выводы из артефактов и запусков, а не приписанные пользователю личные впечатления. Исторический [reflection.md](../reflection.md) сохранён без изменений.

## 7. Сценарий демо на 2–3 минуты — ещё предстоит выполнить

Подготовка вне хронометража: запустить текущую реализацию на отдельной временной БД, не сбрасывая пользовательские данные. Обозначить D сегодняшней локальной датой компьютера с StudyFlow на день показа. Через UI или публичный API создать один курс и задания в таком порядке; реальные ID записать из ответов, цифры в таблице — порядок создания, не требование фиксированных ID.
