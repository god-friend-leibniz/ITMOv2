Подготовка [tasks.md](tasks.md) разрешена, реализация и написание тестов не начинаются. Интеграционные проверки ждут доставки реального шаблона UI, а не повторного технического согласия.

## Summary

Для HTML курса формировать окончательный список all/incomplete/completed/overdue: незавершённость по существующим счётчикам, overdue при дедлайне строго раньше одной текущей локальной даты компьютера с StudyFlow; порядок по дате, отсутствие даты в конце, равенство по числовому ID. В JSON остаётся полный список по ID.

После успешного создания принят способ чтения **существующего полного HTML GET курса**, извлечения маркированной секции и замены только её. Новый HTTP endpoint, JSON-формат, fragment-режим, clock-сервис и инфраструктура не нужны. Сервер вычисляет результат; UI отображает его, проверяет наличие созданного ID и разделяет успех POST/отказ GET. Один `location.reload()` не даёт нужной обратной связи при отказе чтения.

Исследование и рассмотренные альтернативы: [research.md](research.md). Данные: [data-model.md](data-model.md). Проверки после реализации: [quickstart.md](quickstart.md).

## Technical Context

**Language/Version**: Python 3.12; текущие HTML/JavaScript без frontend-сборки.

**Primary Dependencies**: существующие FastAPI/Pydantic, Jinja2, SQLite stdlib, pytest/TestClient; версии из `uv.lock`. UI использует обычные fetch/DOMParser, без новой библиотеки.

**Storage**: существующая SQLite; схема, миграции, записи, владение и каскады не меняются. Derived progress и overdue не сохраняются.

**Testing**: логика — HTTP/HTML через TestClient и реальные временные SQLite-базы; внешний источник времени передаётся явно. Browser/JS-проверки и их реализация принадлежат UI. Текущий общий gate offline/browser/build сохраняется.

**Target Platform**: локальное однопользовательское приложение на loopback; системная локальная дата компьютера с StudyFlow.

**Project Type**: одно приложение с серверным рендерингом и небольшими JS-модулями; отдельный frontend/backend проект не создаётся.

**Performance Goals**: существующий небольшой список без pagination. Дополнительный проход O(n), сортировка O(n log n), память O(n); сетевых вызовов GitHub нет. Требование нагрузки/числовой SLO не задано и не придумывается. Дополнительная передача полного HTML при явном обновлении приемлема для текущего масштаба.

**Constraints**: JSON API и source SQL order ID неизменны; одна локальная дата на результат; без таймеров/опроса/UTC-конверсии; серверный список и has_assignments из одного набора. Маркеры HTML и код UI — зависимость другой команды, не повод добавлять endpoint ради разделения работы.

**Scale/Scope**: один курс и его задания/чек-листы; существующие course и assignment HTML-маршруты. Изменение только в зоне логики и последующей интеграции с UI, без новой доменной сущности.

### Серверное устройство

1. В `studyflow/domain.py` добавить обычные чистые функции `normalize_completion(value)` и `select_course_assignments(assignments, completion, today)`. Первая возвращает допустимый режим или all. Вторая получает нормализованный режим, готовые задания с progress и явный `date`, возвращает новый отобранный и отсортированный список без изменения записей.
2. Завершённость — total > 0 и completed == total; overdue дополнительно требует due_date не null и due_date < today.isoformat(). Канонический YYYY-MM-DD уже гарантирует календарный порядок строк. Ключ порядка: `(due_date is None, due_date or "", id)`; для одинакового отсутствия даты работает ID.
3. В `create_app` предложен keyword-only `local_date_provider=date.today`. Это callable, вызываемый заново, а не дата старта приложения. Курс после чтения сохранённых заданий получает один `date` и передаёт его чистой проекции; источник не вызывается внутри цикла. JSON и маршруту деталей эта дата не нужна.
4. `GET /courses/{course_id}` использует прежний `coursework.list_assignments`. Вычисляет `has_assignments=bool(full_list)` до отбора; передаёт прежние ключи контекста `course`, `assignments`, `completion`, `has_assignments`. Успешный HTML получает `Cache-Control: no-store`. Клиентское свежее чтение также использует no-store.
5. `GET /assignments/{assignment_id}` использует ту же нормализацию, признаёт overdue в return context и формирует `course_url` фактического курса. all остаётся каноническим URL без query; остальные режимы — с completion. Контекст не фильтрует доступ к деталям. Существующие reload задач/изменения деталей сохраняют query, а удаление уже использует `data-course-url`.
6. JSON-маршруты, Pydantic schemas, `coursework.py`, `db.py` и миграции остаются прежними. Не менять общий SQL ORDER BY и не вводить флаг HTML в общий JSON-use-case. `repository`/MCP не участвуют.

### Свежий результат и ошибки

После подтверждённого POST выполняется независимый GET курса. Он заново читает данные и дату; после полуночи результат определяется датой чтения. В HTML требуются одна секция результата, нормализованный режим, has_assignments и ID карточек — полный перечень в [technical-interface.md](contracts/technical-interface.md).

Существующие ошибки сохраняются: отсутствующий курс — HTML 404; занятость — JSON 503 DATABASE_BUSY; неожиданный отказ — безопасная JSON 500 INTERNAL_ERROR. UI проверяет статус до извлечения секции и не предполагает одинаковый media type ошибок. Сеть, неверный HTML или отсутствующие маркеры тоже не являются успешным пустым результатом.

Успешный POST не объединяется с GET в write-транзакцию. Отказ чтения не откатывает сохранение и не вызывает новый POST. Логика гарантирует свежий GET без записи; UI хранит известный успех/ID, показывает сообщение по общему контракту, помечает старый список неактуальным и повторяет только чтение. Неизвестный сетевой исход самой записи не объявляется подтверждённым успехом или гарантированным отсутствием записи.

### HTTP/HTML-проверки и зависимости от UI

| Наблюдаемое поведение | Проверка со стороны логики |
| --- | --- |
| Состав и порядок четырёх режимов | Реальные POST/задачи и GET; перемешанные/равные/отсутствующие даты, пустой/частичный/полный чек-лист, чужой курс. Ожидаемые ID — заранее заданная последовательность примера |
| Fallback и return context | all при отсутствии/пустом/неизвестном completion на обоих HTML-маршрутах; overdue в Back to course и data-course-url; 404 сохраняется |
| Одна текущая дата | Через публичный local_date_provider проверить D и D+1 в одном app и один вызов внешнего источника на результат; не patch domain/db |
| После записи и полуночь | POST при D, независимый GET при D+1, дедлайн D виден в overdue; каждый результат согласован по своей дате |
| Ошибка чтения после POST | Реальная временная SQLite: эксклюзивная блокировка → 503, затем освобождение и GET; для неожиданного отказа — обратимое нарушение только test-БД и восстановление → безопасная 500/повтор. Наличие одного сохранённого ID проверять публичным чтением |
| Пустые случаи, HTML-маркеры, no-store | Проверить контекст/реальный HTML; после доставки UI-шаблона — весь согласованный wrapper и ID карточек, включая has_assignments после первого скрытого создания |
| Сохранность JSON и данных | API до/после HTML остаётся полным по ID с теми же полями/ошибками; HTML GET не пишет. Контроль задания/задач — публичным API, не прямым SQL assertions |

HTTP-граница включает реальный шаблон, но до работы UI его новых маркеров нет. Не создавать альтернативный test-шаблон и не брать шаблоны в зону логики ради прохождения теста. Начальные правила можно проверять текущим HTML/TemplateResponse.context; готовность общего HTML-протокола подтверждается только после реальной интеграции UI.

Имена/состав маркеров, способ использования полного HTML GET и распределение файлов приняты пользователем; по его сообщению UI подтвердил совместимость. Browser-доказательства повторения только GET, обработки сети/неверного HTML, очистки формы, stale-состояния и доступности принадлежат UI. Остаётся зависимость от фактической доставки UI-шаблона; общий контракт не пересматривается.

Планирование Phase 1 завершено; текущий разрешённый этап — подготовка tasks.md без выполнения задач, реализации кода и написания тестов. Прохождение существующего gate проверяет сохранность базового проекта, а не реализацию описанной функции.
