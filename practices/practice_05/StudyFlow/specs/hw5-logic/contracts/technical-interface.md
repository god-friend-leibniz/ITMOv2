# Техническая граница списка курса — версия 0.1

Дата: 2026-10-25. **Статус: интерфейс 0.1 и распределение файлов приняты пользователем; по его сообщению UI подтвердил совместимость в своём плане.** Основание — неизменяемый [общий контракт 1.0](course-list.md). Его требования не пересматриваются. Новый API, маршрут или зависимость не вводятся. Принятие интерфейса не означает доставки шаблона или реализации поведения.

## Запросы и результат после создания

| Этап | Конкретная граница |
| --- | --- |
| Запись | Прежний `POST /api/courses/{course_id}/assignments`, прежний JSON body и ответ `201` с заданием, включая `id` и сохранённый `title`. Поля, статусы и ошибки не меняются. |
| Новое чтение | После подтверждённой записи — обычный `GET /courses/{course_id}?completion={mode}` существующей HTML-страницы. Для all допустим `/courses/{course_id}`. Запросить `Accept: text/html` и `cache: "no-store"`; не использовать старую страницу как новый результат. |
| Формирование на сервере | Текущие задания и прогресс → одна локальная дата → нормализация/отбор/сортировка → обычный `course.html`. Контекст: `course`, `assignments`, `completion`, `has_assignments`; новых JSON-полей нет. |
| Получение UI | Получить HTML как текст, разобрать `new DOMParser().parseFromString(html, "text/html")`, найти секцию ниже. Не навигировать страницу до успеха чтения; не запускать скрипты из полученного документа. |
| Обновление | Заменить только секцию результата вместе с навигацией, карточками и пустым состоянием. Формы и сообщения остаются в текущем документе. Изменение DOM и синхронизация режима выполняются после проверки всего результата. |

Такой GET выполняется после **каждого** успешного создания во всех четырёх режимах. Сегодняшняя дата не передаётся клиенту для вычисления видимости. Если она сменилась между формой, POST и GET, решает дата нового GET.

## Минимальные серверные HTML-маркеры

Принятое изменение `studyflow/templates/course.html` в ответственности UI: обернуть существующую секцию Assignments (заголовок, фильтры, карточки, пустой результат) следующим стабильным контейнером. Это пример границы, а не полная реализация шаблона:

```html
<section id="course-assignment-list"
         data-course-id="42"
         data-completion="overdue"
         data-has-assignments="true">
  <!-- существующие заголовок и навигация -->
  <article class="course" data-assignment-id="103">...</article>
</section>
```

| Маркер | Обязательная семантика принятой границы |
| --- | --- |
| `#course-assignment-list` | Ровно один контейнер результата курса в успешном HTML. Включает навигацию, карточки и пустое состояние; не включает `#assignment-form`, форму курса и сообщения записи/обновления. |
| `data-course-id` | ID курса, из `course.id`. Позволяет проверить, что пришёл ожидаемый курс. |
| `data-completion` | Только нормализованный сервером all/incomplete/completed/overdue. |
| `data-has-assignments` | Строго строка `true` или `false`, из `has_assignments` **до фильтрации**, а не из длины отобранного списка. Непустой результат подразумевает true. |
| `[data-assignment-id]` | На каждой видимой карточке задания, ровно один на карточку, значение — положительный ID. Не ставится на карточку курса или скрытую копию задания. DOM-порядок этих карточек задаёт окончательный серверный порядок. |
| `#assignments-empty` | Сохраняемый существующий элемент при пустом списке; сервер выбирает прежний текст по `has_assignments`. Не создаётся UI как вывод из ошибки чтения. |
| `#assignment-form[data-completion]` | Существующий атрибут и форма остаются вне замены. UI синхронизирует его с режимом нового контейнера; JSON URL формы остаётся прежним. |

Ссылки карточек сохраняют нормализованный контекст режима. Для all допустимо опустить query; для остальных — `?completion={mode}`. Даты, дополнительные JSON-блоки и отдельный список ID в HTML не нужны: видимые карточки уже предоставляют состав.

## Проверка созданного задания

UI сохраняет ID и название из подтверждения POST. Только после успешного нового чтения собирает атрибуты `data-assignment-id` **внутри нового контейнера** и проверяет точное совпадение со строковым представлением сохранённого ID. Название, URL с query, процент или дедлайн не являются идентификатором.

- ID присутствует — отображается полученный список на серверных позициях.
- ID отсутствует — отображается тот же свежий список и предусмотренное общим контрактом подтверждение скрытого создания со ссылкой All фактического курса.
- Чтение неуспешно — членство не установлено; UI не объявляет скрытость или новый пустой результат.

Это проверка наличия ID в готовом результате, а не повтор бизнес-отбора в браузере.

## Успешное чтение и ошибки

Успех HTML-чтения требует `200` с media type `text/html` (параметр charset допустим) и одного контейнера ожидаемого курса с допустимыми режимом и boolean-маркером. UI использует уже нормализованный режим текущей страницы для запроса; новый маркер должен соответствовать ему. Пустой список с false и пустой список с true — оба успешны. Непустой список с false — некорректный результат.

Неуспешный HTTP-статус, ошибка сети/чтения тела, другой media type или отсутствие/некорректность требуемых маркеров — ошибка обновления, а не успешный пустой список. Для этого не нужен универсальный валидатор или проверка UI правильности серверной сортировки.

| Ответ GET | Обработка |
| --- | --- |
| `200 text/html`, корректный контейнер | Использовать секцию, режим и has_assignments как единый результат. |
| `404 text/html` | Существующая страница отсутствующего курса; не извлекать её как список. |
| `503 application/json`, `DATABASE_BUSY` | Существующая ошибка чтения. |
| `500 application/json`, `INTERNAL_ERROR` | Существующий безопасный отказ чтения. |
| Сеть/нечитаемый или неожиданный ответ | Ошибка получения свежего списка. Не требуется единый формат тела для всех ошибок GET. |

HTML курса при успехе получает `Cache-Control: no-store`; клиентское чтение также использует `cache: "no-store"`. Ответы и заголовки JSON API от этого не меняются. Новые ETag, `304`, fragment-режим и служебный JSON endpoint не вводятся.

## Жизненный цикл UI, нужный для этой границы

После подтверждённого POST форма очищается, ID/название сохранены отдельно от чтения. Пока GET ожидает результата, UI показывает ожидание и блокирует повтор запуска этого чтения. При ошибке сохранённое задание остаётся подтверждённым; прежний контейнер и его пустое состояние помечаются неактуальными. UI показывает обязательные «Задание сохранено, но список обновить не удалось» и «Обновить список».

Повтор выполняет только тот же GET для курса/режима, без POST, восстановления сохранённой формы для автоматической отправки или отката. После успешного повтора UI заменяет неактуальный результат; после повторной ошибки остаётся возможность повторить чтение. Сроки жизни сообщений, доступность и безопасный вывод названия — по общему контракту 1.0.

Области сообщений, состояния ожидания/неактуальности и кнопка повтора находятся вне заменяемой секции; кнопка повтора не отправляет форму (`type="button"`). UI выбирает их внутренние селекторы и оформление. Сервер не зависит от этих селекторов. Полученный полный документ не подменяет `body`/формы и не используется для повторного подключения JS.

## Владение и зависимость от доставки UI

- Логика: `studyflow/domain.py`, `studyflow/web.py`, серверный HTML-контекст, дата, `Cache-Control`, HTTP/HTML-проверки. Существующие JSON-маршруты и SQL остаются прежними.
- UI: wrapper/атрибуты в `studyflow/templates/course.html`, новая вкладка и ссылки, обновление в `studyflow/static/assignments.js`, сообщения/повтор, нужный CSS и browser-тесты. `assignment.html` уже использует серверный `course_url`; сохраняется его использование.
- HTTP-проверки маркеров после объединения требуют реального шаблона UI; подменять шаблон специально ради зелёных тестов нельзя. До него серверные правила можно проверять существующим HTML и контекстом ответа, а новую DOM-границу нельзя объявлять готовой.

**Имя и содержимое контейнера, перечисленные маркеры и применение полного GET с извлечением секции приняты.** Подтверждение совместимости UI известно из сообщения пользователя; чужой план для этого не читался. Интеграционные проверки зависят от доставки реального шаблона UI. Продуктовые правила, JSON API и общий контракт 1.0 не меняются.
