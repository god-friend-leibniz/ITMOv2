# Phase 0 research: серверный список заданий

Дата: 2026-10-25. Основания: [спецификация](spec.md), [общий контракт 1.0](contracts/course-list.md), текущий код и тесты этого worktree. Исследование выполнено чтением существующей реализации, включая две независимые проверки серверной проекции и HTML-границы. Код не изменялся, новая функция не демонстрировалась.

До исследования проверена конституция: узкая область изменения, существующая локальная архитектура, неизменность JSON/данных/MCP и HTTP/HTML-граница тестов соблюдаются. Неизвестные технические решения разрешены ниже; открытых продуктовых вопросов нет. После Phase 1 пользователь принял технический интерфейс 0.1 и распределение файлов и сообщил о подтверждении совместимости UI.

## R1. Свежий результат через существующий HTML GET

- **Decision**: после подтверждённого POST UI получает полный HTML обычным `GET /courses/{id}?completion={mode}`, извлекает одну секцию списка и заменяет только её. Используются `fetch` и `DOMParser`, без запуска скриптов из полученного документа.
- **Rationale**: [course.html](../../studyflow/templates/course.html) уже отделяет секцию навигации/заданий от форм. [web.py](../../studyflow/web.py) уже передаёт `course`, `assignments`, `completion`, `has_assignments`. Сохранение формы и сообщения вне заменяемой секции позволяет пережить ошибку чтения после записи.
- **Alternatives considered**: один `location.reload()` теряет управляемую обратную связь при отказе чтения; новый fragment-маршрут или JSON-проекция создают второй формат без потребности; изменение ответа POST нарушает выбранную неизменность JSON API. Передача лишнего HTML приемлема для малого локального приложения.

## R2. Изоляция HTML-проекции от JSON

- **Decision**: добавить в [domain.py](../../studyflow/domain.py) небольшие чистые функции `normalize_completion(value)` и `select_course_assignments(assignments, completion, today)`. Вызываются из HTML-маршрутов; `coursework.list_assignments`, `db.list_assignments` и JSON-маршруты не меняются.
- **Rationale**: [db.py](../../studyflow/db.py) сортирует список по ID; [coursework.py](../../studyflow/coursework.py) добавляет существующий прогресс. Изменение общего SQL поменяло бы API. Отдельная функция над полученным списком локализует правило без нового слоя или иерархии результатов.
- **Alternatives considered**: расширять SQL или общий use case флагами HTML — ненужная связь; оставить бизнес-условия в разрастающемся маршруте — хуже соответствует чистым правилам `domain.py`; отдельный сервис/репозиторий не нужен.

## R3. Завершённость, календарь и порядок

- **Decision**: завершённость определяется `total > 0 and completed == total`. Для overdue дополнительно нужны ненулевой `due_date` и строгое сравнение с `today.isoformat()`. Сортировка новой коллекции по `(due_date is None, due_date or "", id)`; исходный список и записи не меняются.
- **Rationale**: `assignment_due_date` уже допускает только реальные канонические даты `YYYY-MM-DD`. Для них порядок строк совпадает с календарным; отсутствие даты выделено отдельным ключом. Счётчики отбора и показа берутся из одного списка, а процент не используется как независимый статус.
- **Alternatives considered**: UTC/браузерная дата, преобразование дедлайна во время, сохраняемая просроченность и искусственная «максимальная дата» нарушают или усложняют существующий контракт. Повторно разбирать уже валидированные даты при каждом сравнении не требуется.

## R4. Источник времени и свежесть

- **Decision**: предложить keyword-only параметр `local_date_provider=date.today` у `create_app`. Вызвать его один раз после получения сохранённых заданий при формировании каждого успешного результата курса, передать полученный `date` чистому правилу. Успешный HTML курса получает `Cache-Control: no-store`; клиент использует `cache: "no-store"`.
- **Rationale**: default — callable, а не вычисленная при запуске дата. Фабрика уже принимает явные зависимости `db_path` и `summary_reader`; один callable не требует clock-сервиса или DI-контейнера. Повторный GET после POST всегда заново получает дату, включая полночь между записью и чтением.
- **Alternatives considered**: модульная константа или дата формы устаревают; monkeypatch доменных/DB-функций скрывает реальный путь. Таймеры, опрос, ETag/304 и передача сегодняшней даты в HTML не нужны.

## R5. Различение успеха записи и ошибки чтения

- **Decision**: POST сохраняет прежний ответ `201`; следующий GET независим. Успешное чтение — `200 text/html` с ожидаемой секцией и маркерами. Неуспешный HTTP-статус, сеть, неверный тип или отсутствие нужной секции означают ошибку обновления. Повторяется только GET.
- **Rationale**: сейчас HTML 404 возвращается страницей, а безопасные 503/500 — JSON. UI не должен предполагать общий media type ошибок GET. Существующий [assignments.js](../../studyflow/static/assignments.js) выбирает ветку по `completed` и использует один общий `catch`; UI потребуется разделить этапы. Доменная логика не начинает ни запись, ни откат в пути чтения.
- **Alternatives considered**: новый код JSON «сохранено, но…», автоматический повтор POST или общий write+read response протокол не нужны. Неизвестный сетевой исход POST остаётся отдельно от подтверждённого успеха.

## R6. Проверяемая граница и распределение работы

- **Decision**: HTTP/HTML-проверки в [test_assignment_filtering.py](../../tests/test_assignment_filtering.py), реальные временные SQLite-базы, время через публичный параметр фабрики. Ожидаемый порядок задаётся примерами, не повторным вычислением сортировки в тестах.
- **Rationale**: эту границу пользователь прямо включил в ответственность логики. Подход соответствует текущим тестам и TDD/mocking guidance. Ошибки чтения воспроизводятся реальной блокировкой/отказом временной БД с последующим восстановлением; не подменяются `coursework`/`db`/`domain`.
- **Alternatives considered**: тесты приватных helpers, копирование алгоритма в assertions и mocks внутренних слоёв не проверяют публичное поведение. Браузерное доказательство того, что UI повторяет только GET, относится к UI.

Оформление wrapper/карточек, реализация обновления секции и browser-тесты остаются в ответственности UI. Технический интерфейс принят; зависимость интеграции — доставка реального шаблона, а не получение согласия. ADR не нужен: решение обратимо, следует существующему SSR и не меняет архитектурных границ.
