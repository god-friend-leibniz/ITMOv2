# Feature Specification: Порядок заданий и просроченность — логика

**Feature Branch**: `codex/hw5-logic`

**Created**: 2026-10-25

**Status**: Accepted — требования приняты пользователем; соответствует общему контракту 1.0, реализация не начата

**Input**: User description: «На странице курса задания сортируются по дедлайну по возрастанию, без даты — в конце, при равных датах — по ID. Просроченные — незавершённые по чек-листу задания с датой раньше сегодняшней локальной даты компьютера с StudyFlow; они остаются во “Все” и “Незавершённые”. Сортировка действует внутри каждой вкладки. JSON API сохраняет прежнее поведение».

Область ответственности: состав данных, правила отбора и порядка, завершённость, календарная граница, актуальность, пустые результаты и ошибки. Документ описывает необходимый результат для страницы курса. Обязательства обеих сторон закреплены в принятом пользователем [общем контракте 1.0](contracts/course-list.md) и обязательны в полном объёме. Элементы интерфейса остаются в ответственности UI в границах этого контракта. Исходная версия сохранена в spec.initial.md и не изменяется.

## Clarifications

### Session 2026-10-25

Ответы предоставлены пользователем в поручении на уточнение; новых вопросов не задавалось.

- Q: Какие режимы и результат получает UI? → A: completion=all|incomplete|completed|overdue; отсутствие, пустое или неизвестное значение означает all. Сервер предоставляет окончательный список, нормализованный режим и has_assignments до фильтрации (решения 1–2).
- Q: Как определяется дата и видимость после создания? → A: Один результат использует одну актуальную локальную дату компьютера с StudyFlow. После записи видимость устанавливает свежий серверный результат; браузер не вычисляет просроченность, дата открытия формы и дата самой записи не заменяют дату нового результата (решения 3–4).
- Q: Что означает успешная запись при ошибке обновления списка? → A: Сохранение подтверждено независимо от последующего чтения. UI сообщает, что задание сохранено, и предлагает обновить список без повторного создания; ошибка чтения не превращается в ошибку записи или отсутствие совпадений (решение 5).
- Q: Меняется ли JSON API? → A: Существующий контракт сохраняется; механизм получения свежего результата определяется на этапе plan без предписания нового API (решение 6).

При финальной сверке 2026-10-25 пользователь принял согласованные требования и выбрал редакцию contracts/course-list.md стороны представления основой общего контракта 1.0. Проверены текущие спецификации и контракты обеих сторон; содержательных противоречий не обнаружено. Прежние замечания к исходным версиям сохраняются только как история согласования.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Получить задания курса в порядке дедлайнов (Priority: P1)

Студент открывает список заданий своего курса и получает ближайшие по календарной дате задания раньше более поздних, а задания без даты — после всех датированных. Правило одинаково для каждого режима отбора.

**Why this priority**: Порядок нужен всему списку независимо от выбора просроченных и позволяет найти ближайшую работу без ручного сравнения дат.

**Independent Test**: Запросить список курса с набором ниже и сравнить последовательность ID для каждого режима. Другой курс содержит подходящее по дате задание: оно ни в один результат этого курса не попадает.

**Acceptance Scenarios**:

1. **Given** набор A и локальная дата 2026-10-25, **When** получен режим «Все», **Then** последовательность ID равна 30, 10, 20, 40, 50, 60, 70; одинаковые названия и порядок добавления не влияют на результат.
2. **Given** тот же набор, **When** получены «Незавершённые» и «Завершённые», **Then** результаты соответственно 10, 20, 40, 50, 60 и 30, 70, с тем же правилом порядка.
3. **Given** отсутствующий, пустой либо неизвестный режим, **When** запрошена страница курса, **Then** применяется «Все» с новым порядком; ошибка валидации режима не возникает.

Набор A — один существующий курс; completed / total обозначает число завершённых задач / общее число задач:

| ID задания | Дедлайн | completed / total | Завершённость |
| --- | --- | --- | --- |
| 30 | 2026-10-23 | 1 / 1 | Завершено |
| 20 | 2026-10-24 | 0 / 0 | Не завершено |
| 10 | 2026-10-24 | 1 / 2 | Не завершено |
| 40 | 2026-10-25 | 0 / 1 | Не завершено |
| 50 | 2026-10-26 | 0 / 0 | Не завершено |
| 70 | Нет даты | 1 / 1 | Завершено |
| 60 | Нет даты | 0 / 0 | Не завершено |

### User Story 2 - Найти только просроченную незавершённую работу (Priority: P1)

Студент выбирает «Просроченные» и получает незавершённые задания своего курса, дедлайн которых уже прошёл по календарю компьютера с StudyFlow.

**Why this priority**: Это основной новый отбор; неверная граница даты или завершённости меняет смысл результата.

**Independent Test**: Для набора A при дате 2026-10-25 результат «Просроченные» — ровно 10, 20, без потери этих заданий в «Все» и «Незавершённые».

**Acceptance Scenarios**:

1. **Given** набор A, **When** выбран режим «Просроченные», **Then** возвращаются ровно ID 10, 20; сегодняшний, будущий, завершённый и не имеющий даты элементы исключены.
2. **Given** прошлый дедлайн, **When** чек-лист пуст, не начат или выполнен частично, **Then** задание просрочено; при непустом полностью завершённом чек-листе оно не просрочено.
3. **Given** задание просрочено, **When** выбраны «Все» или «Незавершённые», **Then** оно также присутствует в соответствующем результате ровно один раз; «Просроченные» — подмножество, а не отдельное сохранённое состояние.

### User Story 3 - Получить актуальный результат после изменений или смены даты (Priority: P2)

Студент меняет дедлайн или задачи, затем снова запрашивает список курса. Результат отражает сохранённые изменения и сегодняшнюю дату на момент формирования нового результата.

**Why this priority**: Просроченность зависит от меняющихся задач и календаря, поэтому её нельзя зафиксировать при запуске приложения или сохранить как статус задания.

**Independent Test**: Последовательно менять сохранённые задачи и дедлайн и повторно получать список; отдельно проверить два запроса по разные стороны локальной полуночи без перезапуска StudyFlow и создание из формы, открытой до смены даты.

**Acceptance Scenarios**:

1. **Given** задание ID 10 из набора A, **When** завершена последняя незавершённая задача и снова получен список, **Then** задание исключено из «Просроченные» и «Незавершённые», но остаётся во «Все» и попадает в «Завершённые». После повторного открытия задачи снова попадает в «Просроченные».
2. **Given** прошлый дедлайн, **When** добавлена незавершённая задача в завершённый чек-лист либо удалена последняя задача, **Then** следующий результат считает задание незавершённым и просроченным. Удаление единственной незавершённой задачи из оставшегося непустого чек-листа делает его завершённым и исключает из просроченных.
3. **Given** незавершённое задание с датой 2026-10-25, **When** список запрошен 2026-10-25 в 23:59 и затем 2026-10-26 в 00:01 по локальному календарю компьютера с StudyFlow, **Then** в первом результате оно не просрочено, во втором просрочено без перезапуска приложения.
4. **Given** задание ID 10 просрочено, **When** дедлайн сохранён как сегодняшний, будущий либо отсутствующий, **Then** следующий результат исключает его из просроченных и меняет позицию в остальных режимах по новому дедлайну. Возврат прошлого дедлайна восстанавливает членство при незавершённом чек-листе.
5. **Given** форма открыта в «Просроченные» 2026-10-25 в 23:50, введён дедлайн 2026-10-25, **When** задание сохранено и свежий серверный результат сформирован 2026-10-26 после полуночи, **Then** новый пустой чек-лист делает задание просроченным, и оно включено в окончательный список на правильном месте. UI использует этот результат, а не дату открытия формы.
6. **Given** форма открыта 2026-10-25, задание с дедлайном 2026-10-25 успешно сохранено в 23:59, **When** свежий результат для overdue формируется 2026-10-26 в 00:01, **Then** задание включено в просроченные по дате нового результата, хотя на дату записи оно ещё не было просроченным. Все задания этого результата сравниваются с одной датой 2026-10-26.

### User Story 4 - Отличить отсутствие совпадений от ошибки без изменения данных (Priority: P2)

Студент получает корректный пустой результат либо существующую ошибку чтения; сортировка и отбор ничего не меняют в coursework и не требуют GitHub.

**Why this priority**: Отсутствие просроченных не должно выглядеть как потеря заданий или скрытая ошибка, а новые представления не должны менять данные и прежний JSON-контракт.

**Independent Test**: Проверить пустой курс, непустой курс без совпадений, отсутствующий курс и отказ чтения; сравнить сохранённые задания и задачи до и после запросов и JSON-список для набора A. Отдельно проверить ошибку записи и подтверждённую запись с последующей ошибкой чтения списка.

**Acceptance Scenarios**:

1. **Given** существующий курс без заданий, **When** запрошен любой режим, **Then** результат пуст и сообщает, что в курсе нет заданий. Для непустого курса без подходящих заданий результат тоже пуст, но сообщает отсутствие совпадений.
2. **Given** курс не существует или чтение не удалось, **When** запрошен список, **Then** возвращается существующая ошибка, а не успешный пустой результат; данные не изменяются. Ошибки не раскрывают SQL, traceback или секреты.
3. **Given** набор A, **When** JSON-список заданий запрошен до и после просмотра всех режимов страницы курса, **Then** он по-прежнему содержит все задания курса в порядке ID 10, 20, 30, 40, 50, 60, 70 с прежними полями и значениями; передача режима в JSON-запрос не включает отбор или новую сортировку.
4. **Given** успешное создание первого задания курса, **When** свежий серверный результат для сохранённого режима получен после записи, **Then** has_assignments равен true независимо от видимости нового задания. В overdue прошлый дедлайн даёт видимое задание, сегодняшний/будущий/отсутствующий — пустой отбор; во all и incomplete задание видно, в completed — нет. Сравнение выполняется с датой нового результата, а не со старой страницей.
5. **Given** запись отклонена валидацией или завершилась подтверждённой ошибкой без сохранения, **When** UI получает ошибку записи, **Then** подтверждения сохранения нет, учебные данные не изменены, остаётся существующий путь исправления ввода и повтора создания.
6. **Given** запись успешно подтверждена и известен ID нового задания, **When** последующее чтение списка завершается ошибкой сервера или получения результата, **Then** сохранённое задание остаётся в курсе, а ошибка чтения различима с ошибкой записи. UI показывает «Задание сохранено, но список обновить не удалось» и действие «Обновить список» без повторного создания; прежний список и пустое состояние явно обозначены как неактуальные. До успешного чтения не утверждается, что задание скрыто фильтром или что список пуст. Форма очищена после подтверждения записи независимо от исхода чтения.
7. **Given** подтверждённая запись и неудавшееся обновление списка из сценария 6, **When** повторяется только чтение и оно успешно, **Then** UI получает свежий окончательный список, режим и has_assignments, а сохранённое задание учитывается по обычным правилам. Дополнительное задание не создаётся. Если результат не содержит созданный ID, обратная связь о невидимости опирается на этот успешный результат.

### Edge Cases

- Равные дедлайны упорядочиваются по числовому ID по возрастанию. Несколько заданий без даты также упорядочиваются по ID; отсутствие даты не заменяется условной календарной датой.
- Строгое сравнение календарных дат исключает весь сегодняшний день. Дедлайн не становится моментом в UTC и не означает «последние 24 часа». Начало месяца, года и переход через 29 февраля подчиняются тому же правилу.
- При расхождении календарной даты браузера и компьютера с StudyFlow используется дата последнего. Смена системной даты или часового пояса учитывается следующим запросом; дедлайны не преобразуются между часовыми поясами.
- Пустой чек-лист имеет 0 / 0 и 0%, остаётся незавершённым и при прошлом дедлайне включается в просроченные. Завершённость определяется счётчиками, не округлённым процентом и не активностью GitHub.
- Новое задание имеет пустой чек-лист: с прошлым относительно свежего результата дедлайном включается в просроченные, с сегодняшним/будущим дедлайном или без даты — нет. Отсутствие его в успешно полученном результате не означает неудачное создание. Если чтение не удалось, видимость ещё не установлена.
- Некорректная календарная дата по-прежнему отклоняется существующей валидацией записи без частичного сохранения; этот отбор не исправляет данные молча.
- Удалённые задания отсутствуют в следующем результате. Неизвестный режим не превращает отсутствующий курс в успешный пустой курс.
- Неуспешная запись не меняет членство и порядок по несохранённым значениям; успешная повторная попытка учитывается следующим запросом.
- Смена даты между открытием формы, подтверждённой записью и новым результатом разрешается датой формирования нового результата. Исторический состав списка и данные ответа создания недостаточны для самостоятельного решения браузера о просроченности.
- Ошибка чтения после подтверждённой записи не откатывает запись и не разрешает повторное создание как способ обновить список. Старый список не выдаётся за свежий, ошибка не выдаётся за успешное отсутствие совпадений.
- При сетевой ошибке записи без подтверждённого исхода UI сохраняет ввод и режим, не утверждает ни успех, ни гарантированное отсутствие записи и не повторяет запись автоматически. Это не исход «подтверждённый отказ записи» и не основание вводить новый протокол идемпотентности.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Сервер ДОЛЖЕН формировать окончательный список только заданий выбранного существующего курса, без дубликатов, для completion=all|incomplete|completed|overdue («Все», «Незавершённые», «Завершённые», «Просроченные»). Отсутствующий, пустой и неизвестный режим нормализуется к all; нормализованный режим входит в результат для UI.
- **FR-002**: В каждом режиме задания ДОЛЖНЫ идти по дедлайну по возрастанию, затем задания без даты; равные даты и отсутствие даты разрешаются числовым ID по возрастанию. Заголовок, прогресс и порядок создания не являются дополнительными ключами.
- **FR-003**: Завершённым ДОЛЖНО считаться только задание с total > 0 и completed = total; все остальные допустимые состояния чек-листа незавершены. Существующие счётчики и формула прогресса сохраняются; независимый статус задания не вводится.
- **FR-004**: «Просроченные» ДОЛЖНЫ включать ровно незавершённые задания с заданным дедлайном строго раньше опорной сегодняшней даты. «Все» включает каждое задание курса, «Незавершённые» — каждое незавершённое, «Завершённые» — каждое завершённое. Просроченность не исключает задание из первых двух режимов.
- **FR-005**: Опорная дата ДОЛЖНА быть актуальной локальной календарной датой компьютера, на котором работает StudyFlow, определённой заново при формировании каждого результата списка, включая результат после записи. Один результат использует одну опорную дату для всех заданий; дата старта процесса, открытия формы, самой записи, UTC-дата, браузерная дата и пользовательский ввод не заменяют её. Браузер не вычисляет просроченность или отбор самостоятельно.
- **FR-006**: Каждый новый запрос ДОЛЖЕН заново учитывать сохранённые дедлайны и текущие счётчики задач. Смена локальной даты, завершение/повторное открытие, добавление/удаление задачи, изменение/снятие дедлайна, создание/удаление задания учитываются без перезапуска приложения. В рамках одного результата отбор и показываемый прогресс используют одни и те же значения счётчиков.
- **FR-007**: Вместе с окончательным списком сервер ДОЛЖЕН предоставлять has_assignments — наличие любых заданий выбранного курса до фильтрации, по данным нового результата. Успешный результат позволяет отличить пустой курс от непустого курса без совпадений и от ошибки. Оба пустых случая являются обычными успешными результатами, а не отсутствующим курсом.
- **FR-008**: Несуществующий курс, занятость хранилища и неожиданный отказ чтения ДОЛЖНЫ сохранять действующие категории ошибок: соответственно 404, 503 DATABASE_BUSY и 500 INTERNAL_ERROR с безопасным сообщением. Ошибка не подменяется отсутствием совпадений.
- **FR-009**: Просмотр, отбор и сортировка НЕ ДОЛЖНЫ менять задания, задачи, дедлайны, ссылки на репозитории, владение, правила удаления или схему хранения. Прогресс, просроченность, порядок и опорная дата не сохраняются как новое состояние coursework. Действующие правила валидации, атомарности и сохранности записей остаются обязательными.
- **FR-010**: JSON API ДОЛЖЕН сохранить прежнее поведение: полный список заданий курса в порядке ID по возрастанию, прежние поля ресурсов, статусы, валидацию и форму ошибок. Режимы HTML-страницы не изменяют JSON-ответы; новые поля просроченности и новые маршруты для этой фичи не требуются.
- **FR-011**: Вычисление результата ДОЛЖНО работать без запросов к GitHub и MCP и без дополнительной инфраструктуры. Достаточны существующие данные заданий, производные счётчики задач, контекст курса/режима и локальная дата StudyFlow.
- **FR-012**: После успешного создания логика ДОЛЖНА обеспечивать возможность получить свежий серверный результат выбранного курса и режима после записи: окончательный список, нормализованный режим и has_assignments. Он учитывает сохранённое задание, текущие счётчики и одну актуальную локальную дату формирования этого результата. Его членство, а не дата открытия формы или дата ответа создания, определяет видимость нового задания для UI. Технический способ получения результата остаётся этапу plan; прежний ответ JSON-создания не расширяется.
- **FR-013**: Подтверждённый успех записи и исход последующего чтения ДОЛЖНЫ оставаться различимыми. Ошибка чтения не отменяет и не переобозначает успех записи, не подменяется пустым списком или признаком «скрыто фильтром». После подтверждённого сохранения UI сообщает о нём и предлагает повторить только обновление списка без повторного создания. Ошибки самой записи сохраняют существующий контракт; новая операция, откат сохранённого задания и новые коды ошибок не требуются.

### Key Entities *(include if feature involves data)*

- **Course / курс**: владелец набора заданий; его ID задаёт область результата.
- **Assignment / задание**: существующие ID, принадлежность курсу, заголовок, описание, необязательный дедлайн и ссылка на репозиторий. Идентичность и сохраняемые поля не меняются.
- **Checklist / чек-лист и Assignment progress / прогресс**: существующие задачи и производные completed, total, percent; непустой полностью выполненный чек-лист определяет завершённость.
- **Дедлайн**: необязательная реальная календарная дата без времени и часового пояса.
- **Просроченность**: вычисляемое отношение незавершённого задания с датой к опорной сегодняшней дате; не новая сущность и не независимый статус.
- **Результат отбора**: упорядоченные задания выбранного курса и режима, вместе с контекстом для различения пустых состояний; самостоятельной сохраняемой сущностью не является.

### Данные и взаимодействие с UI — общий контракт 1.0

Режимы, окончательный серверный результат, источник даты, актуальность после создания, разделение ошибок и неизменность JSON API соответствуют принятому [общему контракту 1.0](contracts/course-list.md). Таблица фиксирует границу данных; обязательства UI по состояниям записи/чтения, очистке формы, ожиданию и блокировке повторного запуска, доступности и сроку жизни сообщений действуют в полном объёме по контракту. Технический механизм не выбран.

| Направление | Необходимые данные и смысл |
| --- | --- |
| UI → логика | ID курса и completion=all\|incomplete\|completed\|overdue. Пустое, отсутствующее или неизвестное значение означает all. Отдельный параметр сортировки не нужен. |
| Источник данных → логика | Сохранённые задания курса: ID, due_date либо отсутствие даты, completed и total; остальные существующие поля передаются для представления без изменения смысла. Полный список задач не нужен для этого отбора. |
| Окружение StudyFlow → логика | Одна актуальная локальная сегодняшняя дата при формировании результата, включая результат после записи. UI не передаёт часы, часовой пояс, дату или независимый признак завершённости/просроченности как источник истины и не вычисляет просроченность. |
| Логика → представление страницы | Существующий курс, нормализованный режим, окончательно отобранный и упорядоченный список с прежними данными задания и прогрессом, признак наличия заданий курса до отбора (существующий has_assignments). По пустому списку и этому признаку различаются два пустых состояния. |
| Ошибка → представление страницы | Существующий результат ошибки курса/чтения вместо успешного списка. Новые коды и отдельный канал ошибок не нужны. |
| После сохранения → свежий результат | Подтверждение записи содержит прежние сохранённые данные и ID. После записи сервер формирует новый окончательный список, режим и has_assignments; видимость определяется наличием созданного ID в этом успешном результате. Прежний JSON-ответ создания и дата открытия формы не заменяют новый результат. |
| Запись подтверждена → чтение не удалось | Успех сохранения остаётся известен отдельно от ошибки чтения. UI сообщает о сохранённом задании и предлагает повторить только обновление списка. Не утверждает ни ошибку создания, ни успешное отсутствие совпадений, ни скрытость задания. |
| Контекст навигации | Сохраняется выбранный режим при переходе к заданию и обратно, включая сохранение деталей и успешное удаление. Режим не ограничивает доступ к деталям задания; курс возврата определяется самим заданием. |

Опорная дата — часть вычисления логики; передавать её браузеру для расчёта видимости, добавлять в публичный JSON-ресурс или требовать её отображения не нужно. Сообщение «Задание сохранено, но список обновить не удалось», действие «Обновить список» и остальные состояния/сообщения, указанные в контракте 1.0, обязательны. Оформление UI выбирается в этих границах; существующие подписи и JSON-сообщения не локализуются попутно. Способ получения свежего серверного результата, число запросов и перезагрузка страницы здесь не предписываются.

## Success Criteria *(mandatory)*

### Measurable Outcomes

Пять основных условий приёмки:

- **SC-001 — порядок**: Для набора A результаты всех четырёх режимов на 100% совпадают с ожидаемыми последовательностями ID из сценариев 1–2, включая равные даты и отсутствие даты; ни одного чужого задания или дубликата. Покрывает FR-001–002.
- **SC-002 — точный отбор**: Во всех проверках комбинаций «прошлый/сегодняшний/будущий/отсутствующий дедлайн» и «пустой/не начатый/частичный/полностью выполненный чек-лист» включение в просроченные в точности соответствует FR-003–004. Каждое просроченное присутствует также во «Все» и «Незавершённые».
- **SC-003 — актуальность**: В 100% сценариев изменения задач/дедлайна и перехода через локальную полночь новый результат даёт ожидаемый состав без перезапуска, включая создание до/после полуночи из ранее открытой формы (US3.5–US3.6). Один результат не смешивает разные опорные даты; расхождение с датой браузера не меняет правило. Покрывает FR-005–006, FR-012.
- **SC-004 — пустые результаты и сохранность**: Пустой курс и отсутствие совпадений различимы; каждый проверенный отказ чтения возвращает ошибку вместо пустого успеха. После всех запросов списка сохранённые учебные данные равны исходным, а результат доступен без GitHub. В US4.5–US4.7 ошибка записи и ошибка чтения после подтверждённой записи различаются во всех случаях; при повторе только чтения число созданных заданий остаётся равным одному, а успех сохранения не теряется. Покрывает FR-007–009, FR-011, FR-013.
- **SC-005 — совместимость**: Для того же набора и всех режимов страницы JSON-список до и после просмотра совпадает целиком, включая прежний порядок ID, данные и ошибки. Число новых обязательных действий студента для ведения статуса задания — ноль. Покрывает FR-003, FR-010.

## Assumptions

- Сохраняется локальный однопользовательский сценарий StudyFlow: «компьютер с StudyFlow» — компьютер работающего приложения. Его системная локальная дата считается источником истины; настройка/исправление часов не входит в фичу.
- Приоритет этого конкретного изменения над прежним контрактом ограничен порядком HTML-списка, новым отбором и принятым взаимодействием после создания: свежий результат и различение успеха записи/ошибки чтения. Существующие правила завершённости, JSON API, валидация дат и остальные режимы сохраняют смысл. Упоминание в общей спецификации «без overdue automation» не требует фонового механизма: здесь добавляется вычисление при запросе.
- **Граница актуальности**: список является снимком на момент формирования результата. После полуночи, смены часового пояса или изменений в другом окне открытая страница сама не обязана обновляться; новое получение списка использует актуальную дату, включая получение после создания. Отсутствие фонового обновления совпадает с исходной UI-спецификацией. Дата открытия формы не определяет видимость; автоматический таймер и опрос не требуются.
- Значения дедлайнов проходят существующую валидацию при записи. Работа с повреждённым хранилищем не расширяется до восстановления данных; выявленный отказ обрабатывается действующим безопасным механизмом ошибок.
- Зависимости: действующие данные курса/заданий, корректные производные счётчики чек-листов и системный календарь компьютера с StudyFlow. Новые библиотеки, сервисы, сохраняемые статусы и миграции не нужны.
- В этой работе создаются только документы фичи и служебный указатель Spec Kit. Изменение корневой спецификации, приложения и тестов относится к последующей отдельно разрешённой работе; plan, tasks и implement сейчас не запускаются.

### История согласования и финальная сверка

Следующие пункты описывают сравнение исходных версий до уточнений, а не текущие расхождения:

1. **Выбор, результат и возврат**: completion=overdue, fallback в all, серверный список/режим/has_assignments и перенос режима в детали/обратно были совместимыми предложениями обеих сторон и закреплены общим контрактом.
2. **Исходные UI P-03 и вопрос 3** предлагали дату успешного создания. При уточнении закреплена дата свежего результата после записи, в том числе при полуночи между записью и чтением (FR-005, FR-012; UI FR-009 и US4.6). Браузер не вычисляет просроченность.
3. **Исходные UI US4.2 и FR-007** требовали явной связи подтверждения невидимости с успешным свежим результатом. Сейчас это отражено в FR-012 и UI FR-007. Способ получения результата остаётся этапу plan.
4. **Исходные UI US4.4, FR-008, P-04 и исходная логика** не выделяли обязательный исход «сохранено, последующее чтение не удалось». Теперь разделение исходов, обратная связь и повтор только чтения закреплены в FR-013, US4.6–US4.7 и UI FR-011, US4.7.

Для финальной сверки по разрешению пользователя прочитаны текущие spec.md и contracts/course-list.md обеих сторон. Содержательных противоречий не обнаружено. Прежние замечания об отсутствующих уточнениях закрыты; сопоставление исходных версий сохранено также в истории общего контракта 1.0. Пользователь принял требования и выбрал единую редакцию. Принятие контракта не означает реализации: технический механизм остаётся этапу plan; plan, tasks и implement в этой работе не запускаются.
