# Tasks: серверный список курса и просроченность

**Input**: документы `specs/hw5-logic/`: [spec.md](spec.md), [plan.md](plan.md), [research.md](research.md), [data-model.md](data-model.md), [quickstart.md](quickstart.md), [общий контракт 1.0](contracts/course-list.md) и [технический интерфейс 0.1](contracts/technical-interface.md).

**Status**: бэклог подготовлен, задачи не выполнялись. Требования, технический интерфейс 0.1 и распределение файлов приняты пользователем. Подтверждение совместимости UI известно из его сообщения; чужой план не читался. Техническое согласие не является ожиданием; доставка реального шаблона — отдельная зависимость UI-D.

**Tests**: обязательны по запросу пользователя. Только публичная HTTP/HTML-граница через TestClient, реальные временные SQLite-базы, записи через прежний JSON API. Время — внешний явно переданный `local_date_provider`. Не тестировать приватные helpers напрямую, не подменять domain/coursework/db и не пересчитывать ожидаемую сортировку тем же алгоритмом.

**Organization**: фазы по US1–US4 из спецификации, с их приоритетами. Все пути ниже относительно StudyFlow. Зона записи логики: `studyflow/domain.py`, `studyflow/web.py`, `tests/test_assignment_filtering.py` и документы своей фичи. Шаблоны, JS, CSS и новые browser-проверки остаются UI.

## Format: `[ID] [P?] [Story] Description`

- Каждый пункт имеет незавершённый checkbox, уникальный последовательный T-ID, у story-задач — US-label, и точные пути файлов.
- `ТЕКУЩИЙ` — выполнимо с существующим настоящим шаблоном, после своих серверных предпосылок. Это не утверждение, что такое поведение уже реализовано.
- `ИНТЕГРАЦИЯ UI-D` — начинать только после доставки UI-D и соответствующего серверного ядра. До этого пункт остаётся невыполненным/заблокированным; не заменяется skip/xfail, тестовым шаблоном или ручной имитацией HTML.
- `[P]` не используется: задачи логики разделяют исходные файлы и требуют последовательного TDD. Внешняя независимая работа UI описана в зависимостях, а не присвоена этому бэклогу.

## Path Conventions

Одно существующее приложение: `studyflow/`, `tests/`, `scripts/`, `specs/hw5-logic/`. Не создавать новый проект, серверный endpoint, формат JSON, миграцию, clock-сервис или инфраструктуру разделения команд. Общий `coursework.list_assignments` и SQL `ORDER BY id` сохраняются.

## Dependencies & Execution Order

### Внешняя зависимость UI-D

UI-D — доставка/интеграция настоящего `studyflow/templates/course.html` от UI согласно принятому интерфейсу 0.1: контейнер #course-assignment-list, data-course-id/data-completion/data-has-assignments, карточки с data-assignment-id, фильтры и empty внутри контейнера, формы/сообщения вне него. Источник — реальное согласованное изменение UI, а не файл, созданный логикой, render override или test-only шаблон.

Клиентский fetch/DOMParser/замена секции, сообщения/повтор, CSS и новые `tests/test_browser.py` принадлежат UI и **не являются задачами этой команды**. Их готовность и переданная UI проверка нужны для общей демонстрации, но не мешают серверным TDD-циклам на текущем шаблоне. Способ получения чужих изменений не предписывается этим бэклогом; без отдельного разрешения чужие файлы/worktree не читаются и не редактируются.

### Граф серверного ядра и интеграционных gates

```text
T001 → T002 → T003
               ↓
US1 core: T004 → T005 → T006
               ↓
US2 core: T008 → T009 → T010
               ↓
US3 core: T012 → T013 → T014
               ↓
US4 core: T016 → T017 → T018 → T019 → T020

US1 core + UI-D → T007
US2 core + UI-D → T011
US3 core + UI-D → T015
US4 core + UI-D → T021

T007 + T011 + T015 + T021 → T022 → T023 → T024
```

Номера соответствуют порядку фаз; заблокированный UI-D пункт не запрещает перейти к следующему серверному ядру после green. Он остаётся незавершённым и возвращается в очередь после поставки. Не начинать несвязанную работу при неожиданном красном тесте; читать feedback и сначала исправлять его. Сознательный RED ведёт сразу к минимальной реализации того же поведения.

| Класс задач | ID | Количество |
| --- | --- | --- |
| Выполнимы на текущем реальном шаблоне после серверных предпосылок | T001–T006, T008–T010, T012–T014, T016–T020 | 17 |
| Интеграционные HTTP/HTML, требуют UI-D | T007, T011, T015, T021 | 4 |
| Завершающие после интеграции | T022–T024 | 3 |

US1–US2 имеют общий приоритет P1, US3–US4 — P2. Они наблюдаются отдельными сценариями, но реализация последовательна из-за общей проекции и общих файлов. Существующие сущности Course/Assignment/Task не реализуются повторно; новые состояния в БД не добавляются.

### Внутри каждого TDD-цикла

1. Подготовить данные через публичный API и добавить **один** тест недостающего наблюдаемого поведения.
2. Запустить его, убедиться в ожидаемом RED; неожиданные setup/инфраструктурные ошибки не считать полезным RED.
3. Минимально изменить только свою зону domain/web для этого поведения, получить green и прочитать hook feedback.
4. Только затем добавлять следующий сценарий. Если поведение уже green из предыдущего цикла, записать это как проверку, без выдуманной поломки или ненужного кода.
5. Не заменять настоящий UI-шаблон, не менять ожидаемое поведение ради прохождения, не писать заранее все тесты или все слои. Прямой SQL допустим только для обратимого fault setup временной БД, assertions о данных выполняются через публичный API.

## Implementation Strategy

### MVP First

T001–T006 дают минимальный серверный US1: сортировка существующей страницы и регрессия прежнего контракта. Проверить его отдельно на текущем HTML; это не полный релиз overdue и не доказательство готовности нового DOM-интерфейса. После UI-D выполнить T007.

### Incremental Delivery

Продвигать серверное ядро US1 → US2 → US3 → US4 короткими TDD-циклами, возвращаясь к соответствующим интеграционным пунктам после UI-D. Закрывать историю полностью только после её реального HTML-gate. Все 24 пункта относятся к будущей реализации/проверке и сейчас остаются `[ ]`.

Распределение файлов и техническое согласие не пересогласовываются. Общий контракт и исходная версия не меняются. Обновление общей корневой документации при последующей интеграции должно отдельно соблюдать конституцию и разрешённый объём; этот бэклог не даёт права менять её, чужой worktree, UI-файлы или hooks.

## Notes

Итого: **24 задачи**; US1 — 4, US2 — 4, US3 — 4, US4 — 6; Setup/Foundational — 3, завершение — 3. Каждый story-пункт имеет точные пути и US-label; все флажки незавершённые. Ожидание UI-D не обходится skip/xfail. Текущая команда завершает только подготовку бэклога и обновление статуса технических документов; код, тесты и сами задачи не выполняются.
