# Phase 0: UI списка курса

Дата: 2026-10-25. Основания: [принятая спецификация](spec.md), [общий контракт 1.0](contracts/course-list.md), существующие `course.html`, `assignment.html`, `assignments.js`, `style.css`, `tests/test_browser.py` и разрешённые `specs/hw5-logic/plan.md`, `specs/hw5-logic/contracts/technical-interface.md` из worktree логики. Проведён отдельный read-only исследовательский аудит совместимости по workflow speckit-plan; код и тесты не менялись. Внешнее исследование технологий или выбор новых зависимостей не потребовались.

## Решение 1: использовать предложенный HTML-интерфейс 0.1

**Decision**: После каждого подтверждённого создания во всех четырёх режимах читать существующий GET страницы курса с `Accept: text/html` и `cache: "no-store"`, извлекать один `#course-assignment-list` и заменять только его. Сервер отдаёт no-store и окончательный результат. UI принимает предложенные имена/семантику маркеров; существенного несоответствия требованиям нет.

**Rationale**: Сервер решает состав, порядок и дату. Формы и сообщения вне секции переживают обновление и ошибку; ID карточек достаточны для проверки видимости. Это следует принятому контракту без нового API. Цена — передача полного HTML и зависимость от небольшого набора стабильных маркеров; приемлемо для существующего локального списка без пагинации.

**Alternatives considered**: `location.reload()` после POST теряет контролируемое сообщение об успешной записи при отказе чтения; вычисление дат в браузере нарушает контракт; отдельный JSON/fragment endpoint создаёт второй несовместимый способ обмена и не нужен. Внешние DOM-библиотеки и frontend-сборка не нужны.

## Решение 2: проверять результат до единственной замены DOM

**Decision**: Прочитать тело как HTML в отдельный Document через DOMParser; проверить HTTP 200, media type text/html, единственность контейнера, ожидаемые курс/режим, строгий boolean, положительные уникальные ID карточек и непротиворечивое пустое состояние. Только затем импортировать проверенную секцию и заменить прежнюю целиком, синхронизировав режим формы.

**Rationale**: 404 HTML, 500/503 JSON, сетевой отказ и неполный HTML не становятся пустым успехом и не разрушают предыдущую страницу. Импортируется только секция без форм/скриптов; скрипты полного документа не запускаются. Безопасность пользовательских полей сохраняет Jinja-экранирование, а сообщения используют textContent. DOMParser не рассматривается как санитайзер.

**Alternatives considered**: Замена body уничтожает форму и обработчики; ранняя вставка до проверки создаёт частичный результат; собственная проверка правильности дат/порядка в UI дублирует бизнес-логику. Универсальная схема HTML и новый слой валидации не нужны — достаточно конкретных маркеров.

## Решение 3: разделить запись и обновление в текущем assignments.js

**Decision**: Создание страницы курса получает отдельную последовательность POST → GET. Известные ID/title хранятся в памяти текущей страницы. Состояние записи и актуальность списка различаются; повтор ошибки обновления вызывает только функцию чтения. PATCH деталей и DELETE сохраняют нынешние ветви reload/confirm/возврата.

**Rationale**: Сейчас один try/catch и shortcut для completed смешивают успех записи с последующими действиями. Требуется локальная правка обычными функциями, без нового клиентского хранилища или библиотеки состояний. Пока запись/чтение выполняется, повторные действия блокируются; после отказа чтения доступно его повторение. Новая намеренная отправка пустой/изменённой формы не служит повтором уже сохранённого задания; сообщение об ошибке списка не исчезает до успешного обновления/ухода.

**Alternatives considered**: Возврат из completed-ветви без GET нарушает свежесть; общий catch показывает ложную ошибку создания после 201; retry всего обработчика повторяет POST. Отдельный модуль/сервис для двух операций усложняет нынешний небольшой скрипт.

## Решение 4: навигационные ссылки, стабильные сообщения и фокус

**Decision**: Сохранить `nav[aria-label="Assignment completion"]`, обычные ссылки и `aria-current="page"`; добавить Overdue. Внешние к секции области status/alert, видимая stale-пометка, retry type=button и aria-busy дают обратную связь. После успешного retry, если фокус был на скрываемой кнопке, вернуть его к стабильной кнопке Add assignment; при обычном обновлении фокус формы не перехватывать.

**Rationale**: URL и серверный return context уже поддерживают reload/shared URL. Замена навигационной секции не требует повторного подключения JS. Сообщения и форма остаются в документе; вспомогательные технологии получают состояние без пересоздания live-областей.

**Alternatives considered**: ARIA tab widget, SPA history и перехват ссылок добавляют клавиатурный протокол и не нужны. Автоматический фокус на новом задании после каждого создания мешает продолжающему ввод пользователю.

## Решение 5: browser-граница с реальным сервером

**Decision**: Планировать проверки через существующий pytest/Playwright course_server, реальные временные SQLite и HTTP-действия. Серверную полночь контролировать предлагаемым логикой `create_app(local_date_provider=...)` через fixture; ошибку доставки списка — удержанием/отказом конкретного GET на браузерной HTTP-границе. Считать POST/GET и проверять сохранённый ID публичным API.

**Rationale**: Изменение часов браузера не проверяет серверную дату. Проверки реального HTML, формы, сообщений и фокуса обнаруживают интеграционные ошибки, которые не видны через context-only тесты. Ожидаемый порядок задан примерами спецификации, а не копией сортировщика.

**Alternatives considered**: Unit-тесты приватных JS helpers, подмена domain/db, фальшивый test-only шаблон и серверный endpoint для перемотки часов не проверяют нужную публичную границу. Browser-тесты не заменяют HTTP/HTML-проверки логики.

Все существенные неизвестные разрешены предложенным интерфейсом и текущим кодом. На стороне UI интерфейс 0.1 признан совместимым; это план будущей интеграции, а не утверждение, что маркеры, серверные изменения или новые проверки уже реализованы. Изменения внешних технических документов не выполняются.
