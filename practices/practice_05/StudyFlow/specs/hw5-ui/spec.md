# Feature Specification: Список по дедлайнам и вкладка «Просроченные» — UI

**Feature Branch**: `codex/hw5-ui`

**Created**: 2026-10-25

**Status**: Accepted — требования приняты пользователем; соответствует общему контракту 1.0, реализация не начата

**Input**: User description: «Задания курса сортируются по дедлайну по возрастанию, без даты — в конце, равные даты — по ID. Новая вкладка “Просроченные”: незавершённые по чек-листу задания с датой раньше сегодняшней локальной даты компьютера с StudyFlow. Сегодняшние, завершённые и без даты исключены. Просроченные остаются во “Все” и “Незавершённые”. JSON API сохраняет поведение. Ответственность UI: список, вкладки, навигация, пустые состояния, ошибки, создание, доступность и ожидания от логики. Только спецификация».

## Clarifications

### Session 2026-10-25

Решения предоставлены пользователем; дополнительных вопросов не задано. Шесть решений сгруппированы в пять записей.

- Q: Какие режимы и какой результат получает UI? → A: `completion=all|incomplete|completed|overdue`; отсутствующее, пустое или неизвестное значение означает `all`. Сервер формирует окончательный список, нормализованный режим и `has_assignments` до фильтрации.
- Q: Кто определяет просроченность и опорную дату? → A: Сервер использует одну актуальную локальную дату компьютера с StudyFlow на результат; браузер не вычисляет просроченность.
- Q: Чем определяется видимость после создания? → A: Свежим серверным результатом после успешной записи, без использования даты открытия формы или локального вывода из ответа создания.
- Q: Что показывать при успешной записи и неудачном обновлении списка? → A: «Задание сохранено, но список обновить не удалось» и возможность повторить только обновление списка, без повторного создания.
- Q: Меняется ли JSON API? → A: Существующий контракт сохраняется; механизм получения серверного результата определяется на этапе plan.

При финальной сверке 2026-10-25 пользователь принял согласованные требования и единую редакцию [общего контракта 1.0](contracts/course-list.md). Текущие спецификации и контракты обеих сторон прочитаны; содержательных противоречий не обнаружено. История сравнения исходных версий сохранена ниже, исходная копия не изменяется.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Видеть задания в порядке дедлайнов (Priority: P1)

Студент открывает курс и видит задания с более ранними календарными датами первыми, чтобы выбирать работу без ручного поиска.

**Why this priority**: Порядок меняется для всех пользователей страницы курса.

**Independent Test**: Открыть курс с перемешанными и одинаковыми датами и отсутствующими датами; сверить последовательность ссылок во всех вкладках.

**Acceptance Scenarios**:

1. **Given** задания курса с ID 11 (без даты), 12 (2026-10-27), 13 (2026-10-24), 14 (2026-10-24), 15 (без даты), **When** студент открывает «Все», **Then** видит ровно 13, 14, 12, 11, 15 независимо от названий.
2. **Given** в «Незавершённых» и «Завершённых» есть задания с разными и равными датами и без даты, **When** студент выбирает вкладку, **Then** её состав сохраняет прежние правила завершённости, а порядок следует тому же правилу дат и ID.
3. **Given** студент изменил или очистил дедлайн в деталях, **When** возвращается в курс, **Then** задание занимает соответствующее новой дате место, если входит в текущую вкладку.

---

### User Story 2 - Открыть просроченную работу (Priority: P1)

Студент выбирает «Просроченные», чтобы выделить незавершённую работу с уже прошедшим дедлайном.

**Why this priority**: Это основной новый способ отбора заданий.

**Independent Test**: При локальной дате 2026-10-25 открыть вкладку для набора ниже; проверить состав, порядок и отсутствие заданий другого курса.

**Acceptance Scenarios**:

1. **Given** задания из таблицы и локальная дата 2026-10-25, **When** студент выбирает «Просроченные», **Then** видит только 23, 21 в этом порядке.

   | ID | Дедлайн | Выполнено / всего задач | В «Просроченных» |
   | --- | --- | --- | --- |
   | 21 | 2026-10-24 | 0 / 0 | Да |
   | 22 | 2026-10-24 | 1 / 1 | Нет |
   | 23 | 2026-10-23 | 1 / 2 | Да |
   | 24 | 2026-10-25 | 0 / 1 | Нет |
   | 25 | 2026-10-26 | 0 / 1 | Нет |
   | 26 | Нет | 0 / 1 | Нет |

2. **Given** 21 и 23 просрочены, **When** студент открывает «Все» или «Незавершённые», **Then** оба остаются там, каждое ровно один раз, в общем порядке дедлайнов.
3. **Given** студент завершил последнюю незавершённую задачу просроченного задания, **When** возвращается в курс, **Then** оно исчезает из «Просроченных» и «Незавершённых», оставаясь во «Все» и «Завершённых»; после повторного открытия задачи снова подходит «Просроченным».

---

### User Story 3 - Сохранять выбранную вкладку (Priority: P2)

Студент переходит к заданию, меняет его или чек-лист и возвращается к тому же срезу курса.

**Why this priority**: Существующая навигация уже сохраняет фильтр; новая вкладка должна вести себя последовательно.

**Independent Test**: Выбрать «Просроченные» с клавиатуры, перезагрузить страницу, открыть её адрес отдельно и пройти курс → детали → изменение → возврат, затем удаление с подтверждением.

**Acceptance Scenarios**:

1. **Given** выбран любой из четырёх режимов, **When** студент перезагружает страницу или открывает её адрес в другой вкладке браузера, **Then** сохраняются режим и видимый текущий выбор; состав соответствует актуальным сохранённым данным и текущей локальной дате.
2. **Given** задание открыто из «Просроченных», **When** студент сохраняет изменения задания или задач, **Then** детали остаются доступны с контекстом возврата; «Back to course» возвращает в «Просроченные» фактического курса, даже если задание больше не подходит фильтру.
3. **Given** задание открыто из выбранной вкладки, **When** студент подтверждает удаление, **Then** возвращается в ту же вкладку его курса; отмена оставляет детали и данные на месте.
4. **Given** в адресе курса или деталей нет режима либо режим пустой/неизвестный, **When** студент открывает адрес, **Then** используется «Все» без ошибки валидации фильтра; отсутствующие курс и задание сохраняют понятную страницу «не найдено».

---

### User Story 4 - Создавать задания и понимать пустой список (Priority: P2)

Студент создаёт задания из любой вкладки и отличает успешное создание скрытого задания от ошибки или отсутствия заданий в курсе.

**Why this priority**: Новое задание имеет пустой чек-лист, но видимость в «Просроченных» зависит ещё и от даты; молчаливое отсутствие созданного задания вводило бы в заблуждение.

**Independent Test**: Создать задания с прошлой, сегодняшней, будущей и пустой датой из «Просроченных»; повторить скрытое создание из «Завершённых», проверить ошибки записи, отказ последующего чтения, переход через полночь, повторную отправку и оба пустых состояния. Видимость сверять только со свежим серверным списком после записи.

**Acceptance Scenarios**:

1. **Given** открыты «Просроченные» и серверная локальная дата остаётся 2026-10-25, **When** запись задания с дедлайном 2026-10-24 успешна и получен свежий серверный список после неё, **Then** задание видно на правильном месте, вкладка сохранена. Во «Все» и «Незавершённых» UI также показывает полученный серверный список в текущем режиме; способ обновления страницы здесь не задаётся.
2. **Given** открыты «Просроченные» и серверная локальная дата остаётся прежней, **When** запись задания на сегодня, будущее или без даты успешна и свежий серверный результат не содержит его ID, **Then** UI отображает этот результат в той же вкладке, подтверждение с сохранённым названием, объяснением «скрыто текущим фильтром» и ссылкой «Все» этого курса. В «Завершённых» это относится к любому новому заданию с пустым чек-листом. UI не определяет невидимость самостоятельно по дедлайну или ответу создания; поля очищаются после подтверждённого успеха записи.
3. **Given** в курсе нет заданий, **When** получен успешный серверный результат любой вкладки, **Then** при пустом списке и `has_assignments=false` виден `No assignments yet.`; при пустом списке и `has_assignments=true` — `No assignments match this filter.`. Навигация, создание и редактирование курса доступны в обоих случаях. После первого скрытого создания сообщение меняется на отсутствие совпадений только на основании успешного свежего чтения.
4. **Given** отправляется форма создания, **When** запись ожидает результата, **Then** повторная отправка заблокирована, прежнее подтверждение скрыто; **When** запись отклонена валидацией/сервером или её успех не подтверждён из-за сетевой ошибки, **Then** видна соответствующая ошибка, ввод и режим сохранены, подтверждения успеха нет. При подтверждённом отказе записи можно повторить создание; при неизвестном исходе UI не утверждает, что запись отсутствует, и автоматически её не повторяет. Подтверждённая успешная запись с ошибкой чтения обрабатывается отдельно по сценарию 7.
5. **Given** свежий серверный результат подтвердил скрытое создание, **When** студент активирует ссылку «Все», **Then** открывается список того же курса с созданным заданием. Название с разметкой показывается обычным текстом. Подтверждение скрытого создания исчезает при следующей отправке, переходе или перезагрузке, без таймера и сохранения между страницами.
6. **Given** форма в «Просроченных» открыта 2026-10-25 в 23:59, введён дедлайн 2026-10-25, **When** создание успешно завершено после полуночи, а сервер формирует свежий результат 2026-10-26 в 00:01, **Then** новое задание с пустым чек-листом входит в «Просроченные» и видно в правильном месте. Дата открытия формы и дата браузера не используются; подтверждения «скрыто фильтром» нет. Если полночь наступила между записью и последующим чтением, решение также определяется датой нового серверного результата.
7. **Given** сервер подтвердил создание, **When** последующее чтение списка завершилось ошибкой, **Then** UI сохраняет режим и показывает «Задание сохранено, но список обновить не удалось», а также действие «Обновить список». Оно повторяет только чтение текущего курса/режима, не создание. Форма уже очищена после успеха записи; прежний список явно помечен неактуальным, новое пустое состояние или скрытость задания не объявляются. После успешного повтора UI отображает свежий результат и соответствующую ему видимость сохранённого задания; повторная ошибка сохраняет сообщение и возможность повторить чтение. Число созданных заданий остаётся равным одному.

### Edge Cases

- Пустой чек-лист остаётся незавершённым: `0 / 0`, `0%`, `No tasks`; прошедшая дата включает его в «Просроченные». Это не новый статус задания.
- Удаление последней задачи возвращает незавершённость; удаление единственной незавершённой задачи при оставшихся завершённых может убрать задание из «Просроченных». Результат виден при следующем открытии списка.
- Равные даты у просроченных заданий разрешаются возрастанием ID; задания без даты тоже идут по ID в конце каждой подходящей вкладки.
- Следующая загрузка курса, переключение вкладки или перезагрузка после полуночи использует новую локальную дату компьютера с StudyFlow. Автоматическое обновление открытой страницы не требуется.
- Сегодняшнее задание исключено весь локальный день независимо от времени суток; UTC-дата и часовой пояс отдельно открытого браузера не заменяют дату компьютера с приложением.
- Изменение даты на будущую или очистка даты убирает задание из «Просроченных» при возврате, сохраняя вкладку; это не ошибка и не удаление.
- При ошибке чтения сохраняется существующая обратная связь об ошибке; ошибка не представляется успешной пустой выборкой. Недоступность GitHub не блокирует список, фильтры и CRUD.
- Дата свежего серверного результата после записи может отличаться от даты открытия формы и самой записи. Один результат использует одну локальную дату для всех заданий; браузер не сортирует, не фильтрует и не вычисляет просроченность самостоятельно.
- Подтверждённый успех записи не отменяется ошибкой чтения. Пока обновление ожидает результата, UI обозначает ожидание и блокирует повтор этого чтения; после ошибки доступен повтор только чтения. Старое пустое сообщение не представляется актуальным, если свежий список получить не удалось.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Страница курса MUST показывать только его задания по дедлайну от раннего к позднему, затем без даты; равные даты и отсутствие дат разрешаются возрастанием ID. Правило действует в каждой вкладке (US1; US2.1).
- **FR-002**: UI MUST сохранять «Все», «Незавершённые», «Завершённые» и добавлять «Просроченные»: только незавершённые по чек-листу задания с датой строго раньше сегодняшней локальной даты компьютера с StudyFlow. Сегодняшние, будущие, завершённые и без даты исключены. Просроченные остаются во «Все» и «Незавершённых» (US2).
- **FR-003**: Все четыре вкладки MUST иметь понятные названия, видимый и доступный вспомогательным технологиям текущий выбор, управление Tab/Enter и видимый фокус. Порядок чтения и обхода ссылок заданий MUST совпадать с порядком списка; все режимы доступны и при узком окне (US3.1; SC-005).
- **FR-004**: UI MUST использовать `completion=all|incomplete|completed|overdue` и сохранять режим в адресе, при перезагрузке, прямом открытии, переходе в детали, обновлении деталей и возврате/удалении. Контекст режима MUST NOT ограничивать доступ к деталям. Отсутствующий, пустой или неизвестный режим нормализуется сервером в `all` (US3).
- **FR-005**: Карточки MUST сохранять название-ссылку, описание и дедлайн при наличии, счётчики и процент; пустой чек-лист — `No tasks`. Сортировка и вкладки MUST NOT менять данные или вводить ручное завершение задания (US1–US2).
- **FR-006**: UI MUST различать пустой курс и отсутствие совпадений, сохраняя навигацию и формы; существующие ошибки чтения и страницы «не найдено» MUST NOT подменяться пустым списком (US3.4; US4.3; Edge Cases).
- **FR-007**: Создание MUST сохранять вкладку и разделять успех записи и успех обновления. После подтверждённой записи UI MUST запросить свежий серверный результат; видимость определяется наличием сохранённого ID в этом результате. При наличии показывается список с заданием на серверной позиции; при отсутствии — свежий список и подтверждение скрытого создания с сохранённым названием, причиной и ссылкой «Все». Поля очищаются после успеха записи, независимо от успеха последующего чтения. Механизм обновления страницы остаётся этапу plan (US4.1–US4.3, US4.5–US4.6).
- **FR-008**: Формы MUST сохранять подписи, блокировку повторного запроса при ожидании, ввод при ошибке записи и возможность повтора подтверждённо отклонённой записи. При неизвестном сетевом исходе UI MUST NOT объявлять отсутствие записи или автоматически повторять её. Ошибка и подтверждение MUST объявляться вспомогательным технологиям; устаревший успех скрывается перед отправкой; пользовательский текст остаётся обычным текстом (US4.4–US4.5).
- **FR-009**: Сервер MUST формировать окончательно отобранный и упорядоченный список, нормализованный режим и `has_assignments` для курса до фильтрации. Каждый результат использует одну актуальную локальную дату компьютера с StudyFlow и согласованные счётчики отбора/прогресса; учитывает сохранённые изменения. UI MUST использовать серверный результат, без вычисления просроченности в браузере, в том числе после создания. Фоновое обновление не требуется (US1.3; US2.3; US4.6; Edge Cases).
- **FR-010**: Существующие сценарии редактирования курса/задания, чек-листа, подтверждения каскадного удаления и явной загрузки репозитория MUST сохраняться. JSON API MUST сохранять поля, коды/ошибки, нефильтрованный состав списка и порядок по ID, включая обращения с параметрами HTML-фильтра (US3–US4; сохранность действующего контракта).
- **FR-011**: При подтверждённой записи и отказе последующего чтения UI MUST показать «Задание сохранено, но список обновить не удалось» и действие «Обновить список» для повторения только чтения с тем же курсом/режимом. UI MUST пометить прежний список неактуальным, не объявлять новое отсутствие совпадений или скрытость без успешного результата и не повторять создание. Повторное чтение MUST иметь видимое ожидание, защиту от повторного запуска и восстановление после ошибки (US4.7; SC-004).

### Key Entities *(include if feature involves data)*

- **Course / курс**: существующая область списка; задания других курсов исключены.
- **Assignment / задание**: существующее задание с неизменяемым ID, названием, описанием, необязательным дедлайном и прогрессом; новых сохраняемых полей не требуется.
- **Assignment progress / прогресс задания**: существующие выполнено/всего и процент. Завершён только непустой чек-лист со всеми завершёнными задачами; остальные задания незавершены.
- **Просроченное задание**: временная принадлежность к выборке по дедлайну и незавершённости, не сохраняемый статус, оценка или факт сдачи.
- **Текущая вкладка**: выбор представления и контекст возврата, не характеристика задания.

### Граница взаимодействия — общий контракт 1.0

Правила ниже соответствуют принятому пользователем [общему контракту 1.0](contracts/course-list.md). При финальной сверке учтены текущие спецификации и контракты обеих сторон. Технический механизм и алгоритмы остаются этапу plan.

| Пункт границы | Ожидаемые данные и результат для UI |
| --- | --- |
| **P-01: список** | Сервер передаёт окончательный список выбранного курса/режима с прежними данными задания и прогрессом. UI отображает его порядок и состав без собственного отбора/сортировки. Новая сохраняемая отметка завершённости или просрочки не нужна. |
| **P-02: контекст** | Сервер передаёт нормализованный `completion` и `has_assignments` до фильтрации. Принимаются `all`, `incomplete`, `completed`, `overdue`; отсутствующее, пустое или неизвестное значение означает `all`. Это же значение сохраняется в контексте возврата. |
| **P-03: локальная дата** | Сервер использует одну актуальную локальную дату на результат. UI не получает дату для собственного вычисления просроченности и не использует дату формы/браузера; после записи видимость определяется свежим серверным списком. Дата не добавляется в публичный JSON-ресурс. |
| **P-04: сохранение и ошибки** | Прежний результат записи подтверждает сохранённые ID и название, но не принадлежность вкладке. Затем требуется отдельный по смыслу результат свежего чтения. При отказе чтения после успешной записи UI сообщает о сохранении и предлагает повтор только чтения. Ошибки и JSON-контракт остаются прежними; coursework не зависит от GitHub. |

**История согласования — сопоставление исходных спецификаций**:

1. Режимы/fallback, серверный список, `has_assignments`, одна локальная дата, граница завершённости, порядок и прежний JSON-контракт совместимы с FR-001–FR-011 и таблицей взаимодействия исходной спецификации логики. Её предложения о навигации и обновлении при новом запросе приняты в UI.
2. В исходной спецификации логики строка «После сохранения → следующий запрос» описывает учёт записи новым результатом и наличие ID/даты/прогресса в ответе создания, но не требует явно использовать свежий серверный список для решения UI о видимости. Здесь это обязательное правило; дата в браузер для расчёта не передаётся. Исходное UI-предложение передавать достаточный контекст даты заменено.
3. В исходной спецификации логики нет отдельного исхода «запись успешна, последующее чтение неуспешно» и приёмки повтора только чтения. Здесь добавлены FR-011 и US4.7; это дополнение к её правилам ошибок чтения, а не новый код ошибки записи.

Пункты 2–3 описывают пробелы исходной версии, а не текущие расхождения. Свежий результат и дата его формирования отражены в текущих FR-005/FR-012 и US3.5–US3.6 логики; разделение успеха записи и отказа чтения с повтором только чтения — в FR-013 и US4.6–US4.7. UI FR-007/FR-009/FR-011 и US4.6–US4.7 соответствуют этим обязательствам и общему контракту 1.0. Содержательных противоречий не обнаружено. Механизм доставки результата и обновления представления остаётся этапу plan.
