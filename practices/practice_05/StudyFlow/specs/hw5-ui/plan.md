## Summary

В существующей странице курса добавить Overdue к обычным навигационным ссылкам; отображать окончательный серверный порядок во всех режимах. После каждого успешного создания выполнять существующий HTML GET курса, проверять ответ и заменять только `#course-assignment-list`. Формы и доступные status/error/retry-области остаются вне секции. Видимость созданного задания определяется наличием его ID в свежем результате; браузер не вычисляет дату, отбор или сортировку.

Успех POST отделён от GET: при отказе чтения сохранить факт записи, показать «Задание сохранено, но список обновить не удалось», пометить прежний список неактуальным и дать повтор только GET. Текущие PATCH/delete/checklist/repository-сценарии сохраняются. Исследование и альтернативы: [research.md](research.md); состояния: [data-model.md](data-model.md); DOM/HTTP-потребление: [contracts/ui-course-list.md](contracts/ui-course-list.md); будущая проверка: [quickstart.md](quickstart.md).

## Technical Context

**Language/Version**: Python 3.12 и существующие Jinja HTML, обычные JavaScript/CSS. Отдельной frontend-сборки нет.

**Primary Dependencies**: существующие FastAPI/Jinja2, pytest/pytest-playwright и Playwright из frozen `uv.lock`; браузерные fetch, DOMParser, DOM API. Новых пакетов не требуется.

**Storage**: существующая SQLite остаётся ответственностью логики; UI хранит только краткоживущий ID/title и состояния ожидания/актуальности в памяти страницы. Миграций, localStorage и независимого статуса задания нет.

**Testing**: будущие Playwright-сценарии через настоящий course_server и временную SQLite; контролируемый серверный источник даты из плана логики; сбои доставки GET через браузерную HTTP-границу. Серверные HTTP/HTML-тесты принадлежат логике. Реализация позже идёт по TDD через публичное поведение, по одному сценарию за раз; на этом этапе тесты только спланированы.

**Target Platform**: локальный однопользовательский веб-интерфейс StudyFlow на loopback, поддерживаемый текущим Playwright браузер. Системная локальная дата вычисляется сервером.

**Project Type**: существующее SSR-приложение с небольшими JS-модулями, без SPA и отдельного frontend-проекта.

**Performance Goals**: один дополнительный HTML GET на подтверждённое создание, один GET на явный retry. Просмотр не запускает GitHub. Разбор/проверка/замена линейны по размеру полученной секции; передача полного документа допустима для существующего небольшого списка без пагинации. Новые количественные SLO не заданы.

**Constraints**: общий контракт 1.0 и spec.initial.md неизменны; JSON API прежний; только сервер задаёт список/дату/режим/has_assignments. Без нового endpoint, fragment-режима, JSON-блока в HTML, фонового опроса или общего валидатора. Серверные маршруты и алгоритмы не принадлежат UI.

**Scale/Scope**: страница одного курса, его четыре режима и возврат через детали; создание и последующее обновление. Существующие CRUD, каскады, repository и checklist остаются в прежних границах.

### Шаблоны, вкладки и навигация

В `studyflow/templates/course.html` текущая секция Assignments становится единственным `#course-assignment-list` с `data-course-id`, нормализованным `data-completion` и строгим `data-has-assignments="true|false"`. Внутри остаются заголовок, nav, карточки и empty; каждой карточке — data-assignment-id. Сохраняются существующие поля карточек, экранирование и `<time>`. Даты не становятся клиентским источником правил.

Добавить обычную ссылку Overdue с `?completion=overdue`, существующий aria-current для текущего режима и одинаковый стиль всех четырёх ссылок. All канонически ведёт на курс без query. Перенос строк навигации и focus-visible сохраняются на узком экране. Не вводить role=tab/tablist и отдельный клавиатурный протокол.

Форма курса, #assignment-form и все сообщения создания/обновления остаются вне секции. Новые внутренние селекторы UI описаны в [DOM-контракте](contracts/ui-course-list.md). `assignment.html` уже использует course_url и data-course-url; обязательной правки не нужно. `tasks.js` сохраняет query через reload текущего URL. Серверная поддержка overdue в обоих маршрутах — зависимость от логики.

### Получение и применение свежего списка

В `studyflow/static/assignments.js` выделить обычные функции чтения/проверки/применения результата, не общий клиентский слой. Создание на course.html определяется текущей POST-формой и наличием списка; PATCH деталей не переводится в этот поток.

После подтверждённого POST сохранить ID/title отдельно, очистить форму, показать ожидание и прочитать канонический URL **фактического курса и нормализованного текущего режима**. Применить предложенные `Accept: text/html`, `cache: "no-store"`. Не использовать window.location.reload для завершения создания; обычные навигационные ссылки и reload остальных сценариев остаются.

До изменения DOM проверить 200, text/html, ровно один контейнер, совпадение курса и режима, boolean, ID карточек и empty-маркеры. 404 HTML и 500/503 JSON обрабатываются как отказ обновления; тело ошибки не вставляется. DOMParser используется только для разбора в отдельном документе. Импортировать только проверенную секцию без form/script; не вставлять body и не подключать JS заново. Безопасность текста опирается на Jinja escaping и textContent сообщений, не на мнимую санитизацию DOMParser.

Принять результат одной заменой секции без промежуточного пустого состояния; обновить ссылку на текущий контейнер и dataset режима оставшейся формы. Наличие сохранённого ID проверять только внутри нового контейнера. Нет клиентского сортировщика, today, фильтра по percent или чтения дедлайна для определения видимости. Успех снимает stale/ошибку; отсутствие ID даёт предусмотренное hidden-подтверждение с All, наличие — доступную обратную связь о создании и новую карточку на серверной позиции.

### Создание, обновление и восстановление

Состояние записи и состояние актуальности списка отделены, как описано в [data-model.md](data-model.md). Это несколько значений в текущем файле, без отдельной библиотеки. Повторный submit/retry заблокирован во время POST/GET. На отказе записи сохранять ввод; на подтверждённом успехе форма очищается независимо от последующего чтения.

Ошибка GET после записи не должна попасть в старый catch «Could not save the assignment». Сохранить ID/title и известный успех; старый контейнер не менять и пометить неактуальным. Показать точное обязательное сообщение и type=button для повторного GET. Повторная ошибка оставляет сообщение и доступный retry; успешный повтор применяет новый результат с актуальной серверной датой и решает видимость по ID. Повтор не восстанавливает форму для автоматической отправки и не выполняет POST.

Ошибка актуальности остаётся до успешного обновления/ухода. Если пользователь после завершения ожидания намеренно создаёт другое задание, эта ошибка и прошлый подтверждённый контекст не теряются при отказе новой записи; новый успешный POST заменяет последний ID/title и снова запускает GET. Это сохраняет независимость исходов, не вводя очередь созданий или фоновый retry.

PATCH деталей сохраняет прежний reload текущего URL после успеха. DELETE сохраняет confirm, обработку ошибок и переход по data-course-url. Repository и checklist-обработчики не переписываются.

### Доступность и browser-проверки

Role=status для ожидания/успеха и role=alert для ошибок живут вне заменяемой секции. При GET ставить aria-busy на список; при stale показывать текстовую пометку, а не только цвет/прозрачность. Retry доступен Tab/Enter и никогда не submit. Если после успеха retry скрывается с фокусом на нём, переместить фокус на стабильную Add assignment; обычный успешный refresh не забирает фокус у формы. Существующие labels, escaping и focus-visible сохраняются.

Будущие проверки в `tests/test_browser.py` покрывают: четыре режима и точный порядок ссылок; overdue → детали → изменения/возврат/delete; все варианты создания и обязательный GET; оба empty; POST pending и GET pending; network/404/503/500/неверный HTML; повтор только GET с одной сохранённой записью; серверную полночь при иной дате браузера; безопасный title, live-сообщения, фокус retry и навигацию при ширине 360px. Матрица и способ запуска — [quickstart.md](quickstart.md).

Ожидаемые browser fixture изменения ограничены публичным `create_app(local_date_provider=...)`, предложенным логикой. Нельзя подменять domain/db, рендерить фальшивый test-only шаблон или объявлять маркеры готовыми до объединения. Существующие тесты с названием про reload актуализировать по наблюдаемому результату; PATCH/delete/repository-регрессии сохранить. HTTP-проверки сортировки и маркеров не присваивать UI.

## Граница готовности и необходимые изменения другой стороны

Для реальной проверки нужны изменения логики из её плана: серверный окончательный результат во всех режимах, нормализация обоих HTML-маршрутов, has_assignments до отбора, Cache-Control no-store и публичный local_date_provider для временного fixture. Контекст course/assignments/completion/has_assignments остаётся прежней формы. Дополнительных запросов к серверной команде сверх предложения 0.1 нет.

UI доставляет реальные HTML-маркеры и JS; логика после объединения проверяет именно этот шаблон. До этого нельзя выдавать отдельные context-only проверки или существующий baseline gate за доказательство UI-свежести/повтора. Серверные маршруты, pure-алгоритмы, API и миграции UI не меняет. Все артефакты описывают будущие изменения; текущая команда заканчивается на Phase 1, без tasks.md, кода и тестов.
