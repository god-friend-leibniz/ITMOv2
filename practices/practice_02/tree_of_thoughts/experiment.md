# Tree of Thoughts

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- Решение, для которого нужны альтернативы: как описать негативный сценарий отсутствующего обязательного поля `diff` в acceptance criteria `product_management.md`.
- Критерии выбора: подтверждаемость источниками, полезность пользователю, проверяемость и сохранение границы «решение по PR остаётся за человеком».

## Запрос

Использован раздел «Tree of Thoughts» из [prompts.md](../prompts.md): предложить варианты A, B и C для негативного сценария без назначения HTTP-статуса, сравнить их по критериям и подготовить вариант Gherkin.

## Фактический результат агента

Агент выбрал вариант A как минимально инвазивный и полностью подтверждаемый
diff. Его предложенная замена негативного сценария:

```gherkin
Scenario: Негативный — нет ключа "diff" во входе
  Given доступен HTTP-сервис с endpoint /api/reviews
  And я отправляю JSON без ключа "diff", например {}
  When я выполняю POST /api/reviews
  Then ответ не содержит ключа "comment"
```

Этот вариант не был применён: из diff нельзя установить тело HTTP-ответа после
исключения, поэтому утверждение об отсутствии `comment` не доказано.

## Варианты решения

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A. Описать только наблюдаемое поведение текущей реализации | Опирается на прямой доступ `payload["diff"]` в diff; не вводит нового требования. | Утверждение «ответ не содержит `comment`» не доказано: внешний обработчик может сформировать другое тело ответа. Не улучшает ожидаемое поведение для пользователя. | Высокая подтверждаемость локального исключения, но недостаточная полезность и неполная наблюдаемость HTTP-результата. |
| B. Ввести продуктовое требование о контролируемой диагностируемой ошибке | Даёт пользователю предсказуемое поведение; проверяется без выбора HTTP-статуса; не меняет роль человека в решении по PR. | Это новое требование, не вытекающее из текущего diff; статус и схема тела ошибки требуют отдельного решения. | Высокая полезность и проверяемость; требует явного решения человека. |
| C. Убрать негативный сценарий из acceptance criteria | Не добавляет неподтверждённых требований. | Пользовательский сценарий не описывает ошибочный ввод; остаётся только техническая проверка. | Высокая подтверждаемость, но низкая полезность для продукта. |

## Выбор

- Выбранная альтернатива: B.
- Почему: контролируемая диагностируемая ошибка делает ошибочный ввод понятным для инженера, не требует заранее выбирать HTTP-статус и сохраняет финальное решение по PR за человеком.
- Как проверим: integration- и E2E-проверка отправляет `POST /api/reviews` без `diff` и подтверждает диагностическое указание отсутствующего `diff` без ключа `comment`. Конкретный HTTP-статус не задан.

## Что изменили в исходном артефакте

- Файл и раздел: [`product_management.md`](../../practice_01/product_management.md), «Use case» и «User stories и acceptance criteria».
- Изменение: в Use case и негативный Gherkin добавлено требование о контролируемой диагностируемой ошибке при отсутствии обязательного `diff`; связанные integration- и E2E-проверки обновлены этим ожидаемым результатом.
- Что отклонили: A — как недостаточно доказательный для HTTP-ответа и не улучшающий продуктовый контракт; C — как исключающий важный негативный пользовательский сценарий.
