## Few-shot

```text
Прочитай только следующие источники: practices/practice_01/context.md,
practices/practice_01/TRAINING_PR.diff и
practices/practice_01/product_management.md.

Ты улучшаешь артефакт `product_management.md`, разделы «Первый рабочий
сценарий» и «User stories и acceptance criteria». Цель — сделать критерии
приёмки наблюдаемыми, не назначая HTTP-статусы и не выдумывая интеграции,
SLA, аутентификацию или поведение реальной LLM.

Хороший результат:
«When отправляется POST /api/reviews с JSON, содержащим строковый diff,
Then тело ответа содержит строковое поле comment, возвращённое LLM-зависимостью.
And инженер проверяет черновик; решение по PR остаётся вне сервиса».

Плохой результат:
«API должен всегда отвечать 422 при любой ошибке, быстро обрабатывать большие
PR и автоматически отправлять комментарий в GitHub».

Подготовь только предлагаемый новый текст двух указанных разделов. Добавь один
позитивный, один негативный и один граничный acceptance criterion. Для
отсутствующего поля diff опиши наблюдение фактической ошибки или отсутствия
comment, но не требуй конкретный HTTP-статус. Не изменяй файлы и не описывай
ход работы инструментов.
```

## R.C.T.F.

```text
Role: Ты — product analyst, уточняющий критерии приёмки первого сценария
AI-помощника для review pull request.

Context: Разрешено читать только practices/practice_01/context.md,
practices/practice_01/TRAINING_PR.diff и
practices/practice_01/product_management.md. Инженер вручную выполняет review
AS IS; сервис помогает получить черновик, но финальное решение по PR остаётся
за инженером. Поведение HTTP-обработчиков, внешних систем и реальной LLM
неизвестно.

Task: Предложи минимальную правку раздела «User stories и acceptance criteria»
в product_management.md. Устрани неоднозначные формулировки «ошибка и/или» там,
где можно сформулировать проверяемое наблюдение. Сохрани позитивный,
негативный и граничный сценарии. Не создавай новых продуктовых возможностей.

Format: Верни ровно три части: «Наблюдения о текущем разделе», «Предлагаемый
Gherkin» и «Что осталось неизвестным». В Gherkin не указывай конкретные
HTTP-статусы. Не изменяй файлы.
```

## Chain of Verification

```text
Прочитай только practices/practice_01/context.md,
practices/practice_01/TRAINING_PR.diff и раздел «User stories и acceptance
criteria» файла practices/practice_01/product_management.md.

Проверь текущий раздел перед его улучшением. Не раскрывай скрытые рассуждения.
Сначала составь не более пяти проверочных вопросов: об источнике технических
утверждений, наблюдаемости Then-результата, роли человека, отсутствии
приписанных HTTP-статусов или интеграций и наличии граничного сценария.

Для каждого вопроса укажи источник и краткий результат проверки. Затем верни
исправленный вариант только раздела «User stories и acceptance criteria».
Исправляй лишь утверждения, не подтверждённые источниками; не изменяй файлы.
```

## Tree of Thoughts

```text
Прочитай только practices/practice_01/context.md,
practices/practice_01/TRAINING_PR.diff и
practices/practice_01/product_management.md.

Нужно выбрать, как сделать негативный сценарий отсутствующего поля diff
полезным и проверяемым в product_management.md без выдумывания HTTP-статуса.

Предложи ровно три варианта:
A. Описать только фактически наблюдаемое поведение текущей реализации.
B. Сформулировать новое продуктовое требование о контролируемой ошибке без
   выбора статуса.
C. Убрать негативный сценарий из acceptance criteria и оставить его только в
   техническом тест-плане.

Оцени каждый вариант по критериям: подтверждаемость источниками, полезность
пользователю, проверяемость и сохранение границы «решение за человеком».
Выбери один вариант и подготовь замену только негативного Gherkin-сценария.
Если выбор требует решения человека, явно назови его. Не изменяй файлы и не
показывай скрытые рассуждения.
```

## RAG

```text
Разрешённые источники:
1. practices/practice_01/context.md — границы сценария и роль человека.
2. practices/practice_01/TRAINING_PR.diff — реализованный HTTP-путь, передача
   diff и вызов LLM.
3. practices/practice_01/product_management.md — текущий сценарий и критерии
   приёмки, которые нужно улучшить.

Не читай другие файлы и не используй внешние знания.

На основе источников подготовь доказательный вариант раздела «Первый рабочий
сценарий» и раздела «Use case» для product_management.md. Каждое техническое
утверждение снабди ссылкой вида `[источник: файл, уникальный фрагмент]`.
Не добавляй факты об аутентификации, GitHub, статусах HTTP, SLA, истории
ревью или характеристиках LLM. Если нужный факт отсутствует, пометь
`[не подтверждено источниками]`.

Верни только таблицу разрешённых источников, предлагаемый текст двух разделов
и список исключённых неподтверждённых утверждений. Не изменяй файлы.
```

## ReAct

```text
Цель: Подготовить минимальную, проверяемую правку product_management.md для
первого сценария AI-помощника ревьюера.

Доступные входы: practices/practice_01/context.md,
practices/practice_01/TRAINING_PR.diff,
practices/practice_01/product_management.md.

Разрешённые действия:
1. Прочитать каждый из трёх файлов.
2. Найти в product_management.md утверждения без источника или ненаблюдаемые
   acceptance criteria.
3. Сопоставить их с Context Pack и diff.
4. Предложить правку разделов «Первый рабочий сценарий», «Use case» и
   «User stories и acceptance criteria».

Запрещённые действия: не читать другие файлы, не изменять файлы, не выполнять
HTTP-запросы, не додумывать статусы HTTP, интеграции, SLA, пользователей или
поведение LLM.

Максимум действий: 5.

Условие остановки: остановись после подготовки правки. Если для наблюдаемого
результата нужен неизвестный контракт, задай один вопрос человеку вместо
предположения.

Верни таблицу «действие — наблюдение — решение», затем предлагаемый текст
изменяемых разделов и один вопрос человеку, только если он действительно
необходим. Не раскрывай скрытые рассуждения.
```
