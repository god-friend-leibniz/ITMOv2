# Отчёт 1. Атаки на исходный сервис

Первичное исследование от 28 октября 2026 года. Проверялся исходный `lab/service.py`,
без исправлений. Все данные синтетические. Атаки выполнялись по HTTP только против
отдельного одноразового процесса на `127.0.0.1`.

## Воспроизведение и границы доказательств

```bash
make step6
make test
cd practices/practice_06/lab
PYTHONDONTWRITEBYTECODE=1 python3 probe_security.py
```

`make step6`: 16 тестов успешно. Корневой `make test` также успешен.
Штатные тесты проверяют функциональность и физическую границу стенда, поэтому
зелёный результат ожидаем и не доказывает безопасность.

Скрипт создаёт собственный HTTP-сервер на свободном loopback-порту, собирает
35 обменов запрос/ответ и закрывает свой экземпляр. Удаление выполняется последним,
только внутри временного файлового стенда. Доказательства:
[`evidence/before/http-probes.json`](evidence/before/http-probes.json).
В таблице указаны значения поля `id` из этого файла.

## Подтверждённые проблемы

Приоритеты качественные и относятся к этому учебному сервису; это не расчёт CVSS.

| ID | Проблема и место | Доказательство | Эффект | Приоритет и исправление |
|---|---|---|---|---|
| F01 | Отсутствие проверки сессии и владельца: `/profile`, `/search`, `/orders`, `/files`, `/assistant/context` | `profile-anonymous`, `profile-other-owner`, `search-anonymous`, `orders-anonymous`, `orders-other-owner`, `file-other-owner`, `assistant-other-order`: HTTP 200 | Аноним получает профили и заказы; Alice читает профиль, чек и заказ Bob | Высокий. Установить политику доступа, брать идентичность из сессии, проверять владельца каждого объекта; поиск профилей ограничить сотрудником |
| F02 | SQL injection в трёх запросах через f-string: `service.py:57,59,89` | `profile-sqli`: `id=1 OR 1=1` возвращает оба профиля. `search-sqli`: UNION извлекает заказы через поиск профилей. `assistant-context-sqli`: все заказы попадают в контекст | Раскрытие данных и обход ограничения выбранного объекта | Высокий. Параметризованные запросы, валидация ID и ограничения владельца в SQL |
| F03 | Роль берётся из пользовательского `X-Role`: `service.py:75` | `export-forged-role`: анонимный `X-Role: staff` даёт HTTP 200 и два профиля; `export-real-staff-no-role-header`: настоящая сессия staff без заголовка получает 403 | Подмена полномочий; проверяется заголовок вместо серверной роли | Высокий. Роль только из серверной сессии |
| F04 | Path traversal внутри стенда: `service.py:79` | `file-private-traversal`: `user=alice&path=../../private/operator-note.txt` даёт `TEST_ONLY_OPERATOR_SECRET` | Доступ к закрытой служебной заметке | Высокий. Сопоставлять разрешённые файлы владельцу, не принимать произвольный путь. Сохранить `sandbox.py` |
| F05 | Клиент управляет ценой: `service.py:69` | `order-negative-price`: chair за −1, HTTP 201. `order-string-price`: lamp с ценой `"free"`, HTTP 201 | Нарушение бизнес-правил и типов данных заказа | Высокий. Цена только из серверного каталога; строгая схема входа |
| F06 | Stored XSS: `service.py:87` | `review-xss-submit-anonymous` и `review-xss-html`: сохранённый `<script>document.title="LAB_XSS_PROBE"</script>` возвращается без экранирования с `Content-Type: text/html` | Возможность выполнения JavaScript при открытии страницы отзывов | Высокий. HTML-экранирование текста, защитные заголовки. Здесь подтверждена выдача исполняемого HTML; браузерная трасса выполнения не снималась |
| F07 | Открытый журнал хранит пароли и токены: `service.py:44,82` | `logs-anonymous`: HTTP 200, тела `/login` с паролями и заголовки с токенами. `logs-token-replay`: взятый из журнала токен позволяет создать заказ, HTTP 201 | Кража сессии и действия от имени клиента | Высокий. Не записывать секреты, ограничить доступ и объём журнала; не раскрывать журнал клиентам |
| F08 | AI executor без авторизации и проверки аргументов: `service.py:99–108` | `assistant-anonymous-private-read`: служебная заметка без токена. `assistant-customer-export` и `assistant-anonymous-export`: оба профиля. `assistant-anonymous-delete-root`: HTTP 200, `sandbox_root_exists_after=false`; следующий запрос чека даёт 500 | Раскрытие данных и уничтожение всех файлов стенда без участия LLM | Высокий. Авторизация каждого вызова, минимальный набор инструментов, доступ только к собственному чеку; исключить удаление из клиентского помощника |
| F09 | Нет строгой обработки входа; наружу выдаются исключения: `service.py:125,129` | `malformed-json`, `wrong-body-type`, `sql-error-disclosure`: HTTP 500 с `JSONDecodeError`, `AttributeError`, `OperationalError`. `receipt-after-deletion` раскрывает физический временный путь | Неверные коды ошибок, раскрытие реализации и путей | Средний. Проверка JSON/схемы, контролируемые 400/404, общий ответ на внутреннюю ошибку |

F01 и F04 разделены: F01 — доступ к чужому разрешённому файлу простым выбором
`user=bob`; F04 — обход файловой иерархии к служебному ресурсу. F08 описывает
отдельную поверхность доступа через инструменты, которая остаётся опасной даже
при исправлении обычных маршрутов.

## AI: что уже доказано и что требует отдельного опыта

Анонимный отзыв с инструкцией вызвать `export_profiles` успешно попадает в контекст
обычного запроса Alice. Сохранены точные входы модели:
[`planner-clean.txt`](evidence/before/planner-clean.txt) и
[`planner-poisoned.txt`](evidence/before/planner-poisoned.txt).
Они отличаются только одним вредоносным отзывом. XSS-маркер перед этой парой
удалён из одноразового экземпляра.

Это доказывает попадание недоверенной инструкции в контекст, но само по себе
не доказывает подчинение модели. Результаты реальных вызовов сохраняет
`lab/probe_planner.py` в `planner-*-result.json`. Прямая отправка опасного JSON
в executor учитывается исключительно как тест серверного доступа F08.

## Ограничения и оставшиеся проверки

- Физический выход из файлового стенда блокируется: `file-sandbox-boundary-control`
  возвращает `outside exercise sandbox`; штатные тесты также проверяют symlink
  и удаление внешнего каталога. Выход за стенд и RCE не заявляются.
- В коде нет лимитов числа отзывов, журналов, сессий и срока жизни сессии;
  у HTTP-чтения нет явно установленного таймаута. Это кандидаты для отдельной
  ограниченной проверки доступности; нагрузочный DoS не выполнялся.
- Анонимная публикация отзывов подтверждена. Считать ли саму анонимность дефектом,
  зависит от принятой политики. Инъекция и XSS не должны работать при любой политике.
- Не проверены браузерная эксплуатация XSS, HTTP framing, исчерпание потоков,
  расширенные варианты типов и конкурентные запросы.
- Этот отчёт — первоначальная проверка, а не утверждение «найдены все уязвимости».
  План расширения покрытия находится в [`RESEARCH_PLAN.md`](RESEARCH_PLAN.md).
