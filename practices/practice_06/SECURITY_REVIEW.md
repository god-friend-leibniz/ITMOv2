# Независимая повторная проверка безопасности

30 октября 2026 года. Проверена версия после первого исправления F01–F09.
Три субагента независимо исследовали (1) авторизацию, SQL и бизнес-логику,
(2) HTTP и доступность, (3) файлы, AI и утечки. Основной агент проверил выводы,
внёс дополнительные исправления и выполнил интеграционные проверки.

**Вывод:** первое исправление не устранило все проблемы. Повторная проверка
нашла три остаточных риска безопасности и одну ошибку целостности чека;
они исправлены. Обходов авторизации, SQL-инъекций, чтения private/чужих чеков,
XSS и выполнения запрещённых AI-инструментов после этих изменений не выявлено
в перечисленных проверках. Это не доказательство отсутствия любых уязвимостей.
Известные остаточные ограничения перечислены ниже отдельно.


Для новых регрессий отдельно:


  До исправления новые тесты воспроизводили проблемы: 4 провала в auth/business
  и 46 проваленных проверок/subTest в HTTP. Выводы сохранены в
  `evidence/reaudit/auth-tests-before.txt` и `transport-tests-before.txt`.
- После исправления проходят все **55 тестов** практики, включая исходные
  36. Итоговые протоколы — `evidence/reaudit/make-step6.txt` и `make-test.txt`.
- Расширенная матрица файлов/AI: **281 проверка Shop**, включая исходные 177,
  и **47 HTTP-проверок**. Результаты — `files-ai-after.json` и
  `files-ai-http-after.json`, воспроизводящие скрипты лежат рядом.

  120 конкурентных смешанных покупок сохранили уникальные ID и владельцев.

- Framing: неоднозначные длины, TE+CL, folded headers, дубликаты токенов,

  `framing-before.json`. Результаты Host/slow-read до исправления —

- `service-before.py` — снимок версии перед этим повторным исправлением,
  для сопоставления находок; это доказательство, а не запускаемая версия сервиса.
  `sandbox.py` не изменён. Прежние `evidence/before/` и `evidence/after/`
  сохранены; они относятся к первому этапу проверки.

Все серверы одноразовые и привязаны к 127.0.0.1. Данные синтетические.
Нагрузочный DoS, атаки на посторонние процессы и внешние системы не выполнялись.
Количество assertions и число тестовых методов — разные показатели; они не
складываются в оценку вероятности безопасности.

## Остаточные риски и границы вывода

1. **Account lockout остаётся компромиссом лимитера.** Десять неверных попыток
   за минуту временно препятствуют и правильному входу этого аккаунта.
   Повторение атакующим может продлевать помеху. Это воспроизведено на трёх
   временных окнах и не объявляется исправленным. Пропуск правильного пароля
   при переполненном бакете разрушил бы ограничение перебора. Для открытого
   сервиса нужна отдельная политика client/source rate limiting и восстановления;
   у локального стенда все сетевые клиенты имеют loopback-адрес.
2. Учебные пароли, в том числе staff, публичны по конструкции задания. Знание
   такого пароля даёт штатные полномочия аккаунта. Это не пригодная для публичного
   развёртывания аутентификация. Нет HTTPS, внешней идентификации, хранения
   постоянных данных, платёжной системы и промышленного HTTP-сервера.
3. Лимиты и deadline ограничивают ресурсы отдельного соединения; непрерывный
   поток новых соединений всё ещё может мешать доступности. Распределённый DoS
   не моделировался. Общий deque из 200 отзывов сохраняет только последние записи:
   авторизованный пользователь способен вытеснять старые отзывы. Это текущая
   политика временного хранилища, а не гарантия сохранности публикаций.
4. Между resolve и чтением fixture-файла есть файловая гонка при отдельной
   локальной возможности менять файлы процесса. Через HTTP такой возможности
   нет; удалённый обход не подтверждён. Новые чеки формируются из БД и этой
   файловой операции не используют.
5. Проверки выполнены на Python 3.14; отдельный прогон на Python 3.10 не
   выполнялся. Грамматика authority проверяется явно, независимо от urlsplit.
   Реальная LLM, браузерное выполнение XSS и полная DNS-rebinding цепочка не
   запускались. Проверена серверная граница полномочий, в том числе при
   принудительной передаче опасного решения модели.

Итак, утверждение «уязвимостей больше не осталось» результатами не обосновано.
Обоснован более узкий вывод: перечисленные R01–R04 исправлены, защитные
регрессии проходят, новых обходов проверенных границ доступа не обнаружено;
перечисленные ограничения остаются явными.

## Дополнение при завершении сдачи

Фраза выше об отсутствии реального модельного прогона относится к этапу
технического аудита. Позднее выполнены четыре отдельных прогона планировщика
через свежих субагентов Codex; исходные ответы и HTTP-проверки —
`evidence/model-validation/`, интерпретация — в `REPORT_02.md`. Это не
OpenCode/VSELLM и не проверка браузерной цепочки. Новый исход не меняет
сделанных ранее выводов о пределах доказательств.
